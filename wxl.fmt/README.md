## wxl.fmt

Кастомный буфер и построитель текста поверх библиотеки [fmt](https://github.com/fmtlib/fmt): компоненты `text_buffer` и `text_builder`, и функция `format` — текст для интерфейса одним вызовом.  
Модуль для подключения: `import wxl.fmt;`, таргет сборки: `wxl::fmt`.

## Ключевые архитектурные решения

- **Почему `fmt`, а не `std::format`**  
    Построителю необходим прямой рендеринг в целевой буфер без промежуточных шагов. Стандартный `std::format` не предоставляет такой точки расширения: `format_to` с итератором `back_inserter` посимвольно разбивает вывод на `push_back`, `format_to_n` использует внутренний стековый буфер с последующим копированием, а `formatted_size` и вовсе требует второго полного прохода по данным. Библиотека `fmt` изначально спроектирована вокруг концепции буфера (`fmt::basic_memory_buffer`), и наш `text_buffer` — это его адаптация под аллокаторы wxl.
- **Почему это отдельный модуль**  
    Библиотека `fmt` является внешней зависимостью, в то время как базовый модуль `wxl.core` принципиально изолирован от стороннего кода и зависит исключительно от стандартного модуля `std`. Вынос построителя в `wxl.fmt` защищает проект от раздувания: исходники `fmt` компилируются только тогда, когда приложению действительно необходима производительная сборка текста. Остальная часть кодовой базы эту зависимость не видит.
- **Почему fmt — модуль, а не заголовки**  
    `wxl.fmt` пишет `import fmt;`, и fmt для этого собирается модулем из своих исходников (`src/fmt.cc`, через `FetchContent`; порт vcpkg модуля не даёт). Заголовки fmt в глобальном фрагменте модуля рядом с `import std;` сливаются со стандартной библиотекой только там, куда дотягивается обходной приём MSVC, и `fmt/std.h` (`<thread>`, `<filesystem>`) уже за его пределами. Модулю, который сам делает `import std;`, смешивать нечего. Макросы через модуль не проходят, поэтому вместо `FMT_COMPILE("…")` пишется литерал `"…"_cf` из `fmt::literals`.
- **Почему используется пространство имён `wxl::core`**  
    Если бы стандартная библиотека C++ предоставляла прямой доступ к своему форматирующему буферу, эти компоненты изначально являлись бы частью ядра. Чтобы сохранить монолитность архитектуры, интерфейсы используют общее пространство имён: `wxl::core::text_builder<sta_allocator>`. Наличие отдельного модуля проявляется только на этапе объявления импорта.

Подробный разбор внутреннего устройства и результаты замеров производительности читайте в [технической документации](doc/fmt.md).

## `format` — текст для интерфейса

```cpp
import wxl.fmt;

u16_text text = format(u"{:.9g}", root);   // double или std::complex<double> — девять цифр у каждой части
```

Форматная строка — литерал, который `fmt` проверяет по аргументам на этапе компиляции (или `u"…"_cf` из `fmt::literals`). Результат — проверенный UTF-16 (`u16_text`), и проверки для этого не нужно: аргументами принимаются только числа, чей текст — ASCII, `std::complex` из них — печатается как `(re+imi)`, спецификация числа применяется к обеим частям — и уже проверенный текст (`u16_view`, `u16_text`). Сырой `std::u16string_view` или одиночный `char16_t` не компилируются — они внесли бы в результат свою неизвестную корректность; текст извне сначала проходит `checked()`.
