# Как вносить изменения

*English version: [CONTRIBUTING-EN.md](CONTRIBUTING-EN.md)*

Правила одни для всех, кто вносит правки. Их держит GitHub —
набор правил ветки `main` и проверки CI, — а не договорённость.

## Ветка `main`

- `main` меняется только через pull request с зелёным CI.
- Набор правил GitHub запрещает прямой push и force-push, требует линейной
  истории и разрешает вливание только squash. PR вливает очередь слияния
  (merge queue), проверив сначала, каким станет `main`, и сжимает его в один
  коммит: один PR — один коммит в `main`. Ветку влитого PR GitHub удаляет
  сам.

## Ветка и pull request

- Изменение живёт в ветке `wxl-<тема>`: строчные буквы и дефисы, например
  `wxl-effects-catalog`.
- Pull request открывается из этой ветки в `main`. Один PR — одна тема.
- Заголовок PR становится заголовком его коммита в `main`: он пишется так
  же, как заголовок коммита (ниже).
- Обновлять ветку только потому, что `main` ушёл вперёд, не нужно: очередь
  слияния сама ставит PR поверх `main` и проверяет результат.
- Отправленная ветка не переписывается: ни force-push, ни rebase уже
  отправленного. Если ветка отстала от `main` или конфликтует с ним, `main`
  вливается в ветку: кнопкой «Update branch», а если GitHub влить его не
  может, — локально, слиянием текущего `main` этого репозитория с
  конфликтом, разрешённым в коммите слияния, и обычным push.

## CI

- [`.github/workflows/ci.yml`](.github/workflows/ci.yml) на Windows-раннере
  собирает дерево в Debug и Release, прогоняет все тесты и запускает пример
  `sample.hello` ([`samples/HelloHere`](samples/HelloHere)): у него должно
  появиться окно. Третья строка, `Strict`, собирает и прогоняет тесты
  `wxl.async` с проверками корутин (`WXL_STRICT_CORO`). Там же задача
  `commits` проверяет коммиты PR (ниже).
- Сборка на Windows идёт в очереди слияния — на кандидате: `main`, PR,
  стоящие в очереди впереди, и этот PR, то есть на том, что станет `main`.
  Падает она — PR выходит из очереди, `main` не меняется. Вручную её
  запускает кнопка «Run workflow».
- Своей сборки на Windows у PR нет: строки `build (…)` сразу отчитываются
  успехом, чтобы очередь приняла PR. На PR проверку ведут задача `commits` и
  сайт документации.
- [`.github/workflows/docs.yml`](.github/workflows/docs.yml) на Linux строит
  сайт документации; предупреждение Doxygen — ошибка.
- Обязательные проверки: `build (Debug)`, `build (Release)`, `build (Strict)`,
  `build` (сайт документации) и `commits`. Все должны быть зелёными.

## Коммиты

Правила 1–5 проверяет задача `commits` для каждого коммита PR; номер правила
стоит в её сообщении об ошибке.

1. Адреса автора и коммитера — вида `…@users.noreply.github.com` (настройка
   GitHub «Keep my email address private»). Коммит, который делает сам
   GitHub (слияние кнопкой «Update branch», squash в очереди слияния), имеет
   коммитером `GitHub <noreply@github.com>`; такой коммитер допускается
   только с подписью, которую GitHub подтверждает.
2. В сообщении нет таких строк: `Co-Authored-By` (у коммита один автор),
   строк-баннеров, строк-трейлеров со ссылками.
3. Скрытые каталоги и файлы (`.…`) не часть репозитория; дерево хранит
   только перечисленные в проверке.
4. Подпись — только та, которую GitHub подтверждает; неподписанный коммит
   проходит.
5. Коммит слияния только вливает `main` в ветку: два родителя, второй из
   них — коммит `main`; любое другое слияние проверку не проходит. Сам
   `main` остаётся линейным: очередь сжимает каждый PR в один коммит.

Сообщение — по-английски, в стиле индустрии: короткий заголовок в
повелительном наклонении, пустая строка, в теле — зачем и почему.

## Код

- Перед PR локально проверяйте только то, что задето правкой, в Debug:
  `tools\build.ps1 -Target <цель>` и свои тесты
  `ctest --preset x64-debug -R <тест>` (тесты собираются при
  `-Define BUILD_TESTING=ON`). Полная матрица — дело CI в очереди слияния.
- Подготовка машины и сборка — в [README.md](README.md#быстрый-старт) и
  [docs/building.md](docs/building.md).
- Комментарии и документация пишутся так же, как соседние в том же модуле;
  как строится и проверяется сайт, описано в
  [docs/building.md](docs/building.md#сайт-документации).

## Ошибки

- Каталог [`bugs/`](bugs) хранит воспроизведения дефектов, отправленных
  разработчикам стороннего ПО.
