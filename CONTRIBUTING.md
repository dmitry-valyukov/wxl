# Как вносить изменения

*English version: [CONTRIBUTING-EN.md](CONTRIBUTING-EN.md)*

Документ описывает порядок внесения изменений в репозиторий: именование
веток, pull request, проверки CI и требования к коммитам. Соблюдение этих
требований проверяется автоматически — набором правил ветки `main` на GitHub
и заданиями CI. Автоматически не проверяется только одно требование: уже
отправленную ветку не переписывают (см. раздел «Ветка и pull request»).

## Ветка `main`

- Изменения попадают в `main` только через pull request, у которого
  успешно пройдены все обязательные проверки CI.
- Набор правил (ruleset) ветки `main` запрещает прямой push и force-push,
  требует линейной истории и допускает вливание только способом squash.
- Pull request вливается через очередь слияния (merge queue): перед
  вливанием CI проверяет то состояние, которое примет `main`, после чего
  очередь объединяет pull request в один коммит. Таким образом, каждому
  pull request соответствует один коммит в `main`. После вливания GitHub
  удаляет ветку pull request автоматически.

## Ветка и pull request

- Изменение разрабатывается в отдельной ветке с именем `wxl-<тема>` из
  строчных латинских букв и дефисов, например `wxl-effects-catalog`.
- Pull request открывается из этой ветки в `main` и содержит изменения
  одной темы.
- Заголовок pull request становится заголовком его коммита в `main`, а
  описание — телом этого коммита. Поэтому заголовок и описание пишутся по
  тем же правилам, что и сообщение коммита (см. раздел «Коммиты»), и
  правило 2 распространяется на них.
- Обновлять ветку только из-за новых коммитов в `main` не требуется:
  очередь слияния применяет pull request поверх текущей `main` и проверяет
  результат.
- Уже отправленную ветку не переписывают: force-push и rebase отправленных
  коммитов не допускаются. Если ветка отстала от `main` или конфликтует с
  ней, `main` вливается в ветку командой «Update with merge commit» кнопки
  «Update branch» (не «Update with rebase»). Конфликт разрешается в
  редакторе GitHub «Resolve conflicts» или локально: текущая `main` этого
  репозитория сливается в ветку, конфликт разрешается в коммите слияния,
  и результат отправляется обычным push.

## CI

- Workflow [`.github/workflows/ci.yml`](.github/workflows/ci.yml)
  выполняется на раннере Windows. Он собирает дерево в конфигурациях Debug и
  Release, запускает все тесты и пример `sample.hello`
  ([`samples/HelloHere`](samples/HelloHere)), который должен открыть окно.
  Конфигурация `Strict` собирает и запускает тесты `wxl.async` с включёнными
  проверками корутин (`WXL_STRICT_CORO`). Задание `commits` того же workflow
  проверяет коммиты pull request (см. раздел «Коммиты»).
- Сборка на Windows выполняется в очереди слияния и проверяет кандидата на
  вливание: текущую `main`, pull request, стоящие в очереди раньше, и
  данный pull request. Если сборка завершается ошибкой, pull request
  исключается из очереди, а `main` не меняется. Вручную workflow
  запускается кнопкой «Run workflow».
- Для самого pull request сборка на Windows не выполняется: проверки
  `build (…)` сразу завершаются успешно, чтобы pull request можно было
  поставить в очередь слияния. На этапе pull request выполняются задание
  `commits` и сборка сайта документации.
- Workflow [`.github/workflows/docs.yml`](.github/workflows/docs.yml)
  собирает сайт документации на Linux; любое предупреждение Doxygen
  считается ошибкой.
- Пакеты NuGet CI восстанавливает в режиме блокировки
  (`RestoreLockedMode=true`): изменение закреплений (`tools/packages.json`)
  приходит в одном коммите с файлом `tools/packages.lock.json`, который
  записало обновление пакетов (`tools\build.ps1 -UpdatePackages`); новые
  версии при прежних закреплениях приходят так же, только с этим файлом.
  Файл, который не соответствует закреплениям, останавливает восстановление
  NuGet, а отсутствие файла останавливает настройку
  (`cmake/wxl_packages.cmake`; см.
  [docs/building.md](docs/building.md#пакеты-nuget-и-проекция-cppwinrt)).
- Обязательные проверки: `build (Debug)`, `build (Release)`,
  `build (Strict)`, `build` (сайт документации) и `commits`. Pull request
  вливается, только когда все они завершились успешно.

## Коммиты

Задание `commits` проверяет на соответствие правилам 1–5 каждый коммит
pull request, а в очереди слияния — коммит, в который очередь объединяет
pull request; в сообщении об ошибке указан номер нарушенного правила.

1. Адреса электронной почты автора и коммитера имеют вид
   `…@users.noreply.github.com` (настройка GitHub «Keep my email address
   private»). Коммитер `GitHub <noreply@github.com>` указывается у
   коммитов, которые создаёт сам GitHub (слияния через «Update with merge
   commit» и «Resolve conflicts», объединение в очереди слияния); такой
   коммит допускается только с подписью, которую подтверждает GitHub.
2. Сообщение коммита не содержит строк `Co-Authored-By` (у коммита один
   автор), строк-баннеров и строк-трейлеров со ссылками. То же относится к
   заголовку и описанию pull request: из них составляется сообщение
   коммита, в который очередь объединяет pull request.
3. Скрытые каталоги и файлы (с именем, начинающимся с точки) в репозиторий
   не добавляются, за исключением перечисленных в проверке.
4. Подписывать коммит не обязательно; если подпись есть, GitHub должен её
   подтверждать.
5. Коммит слияния допускается, только если он вливает `main` в ветку: у
   него два родителя, и второй из них — коммит `main`. Любой другой коммит
   слияния проверку не проходит. История самой `main` остаётся линейной,
   потому что очередь объединяет каждый pull request в один коммит.

Сообщение коммита пишется по-английски в общепринятой форме: краткий
заголовок в повелительном наклонении, пустая строка, затем описание того,
что изменено и почему.

## Код

- Перед открытием pull request достаточно собрать и проверить в
  конфигурации Debug только цели, затронутые изменением:
  `tools\build.ps1 -Target <цель>` и соответствующие тесты
  `ctest --preset x64-debug -R <тест>` (тесты собираются с ключом
  `-Define BUILD_TESTING=ON`). Полную матрицу конфигураций проверяет CI в
  очереди слияния.
- Подготовка машины и сборка описаны в
  [README.md](README.md#быстрый-старт) и
  [docs/building.md](docs/building.md).
- Комментарии и документация оформляются так же, как соседние в том же
  модуле. Сборка и проверка сайта документации описаны в
  [docs/building.md](docs/building.md#сайт-документации).
