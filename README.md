# wxl

*English version: [README-EN.md](README-EN.md)*

**wxl (WinUI XAML-Less)** — экспериментальная C++23 библиотека для разработки
настольных приложений под Windows. Позволяет декларативно описывать
интерфейс **WinUI** непосредственно в исходном коде, не прибегая к XAML.

Архитектура библиотеки базируется на собственном генераторе проекций
**winui-srcgen**: на основе метаданных `.winmd` и конфигурационного профиля он
создаёт легковесные обёртки только для требуемых типов. Все
демонстрационные приложения представляют собой классические неупакованные
исполняемые файлы (`unpackaged Win32`), которые готовы к запуску
непосредственно из директории сборки без предварительного развёртывания.

## Архитектурный манифест

Официальный стек разработки под Windows (**WinUI** + C++/WinRT + XAML) обладает
тремя фундаментальными недостатками:

- **Разделение языковой среды:** интерфейс описывается на XAML, что требует
  промежуточного компилятора, генерации IDL-файлов и хрупкого связывания
  элементов с C++ кодом по строковым именам.
- **Избыточная нагрузка на компилятор:** тяжеловесные заголовочные файлы
  проекции `cppwinrt` вынужденно парсятся каждой единицей трансляции, в
  которой упоминается хотя бы один UI-компонент.
- **Накладные расходы в Runtime:** каждый объект представляет собой
  полноценный COM-компонент, генерирующий постоянные запросы интерфейсов
  (`QueryInterface`) и атомарные межпоточные счётчики ссылок, несмотря на
  то, что весь интерфейс работает в одном потоке.

Архитектура **wxl** предлагает альтернативный подход:

- **Изоляция проекции WinRT.** Тяжеловесные заголовки `cppwinrt`
  компилируются лишь однажды — при сборке самой библиотеки `wxl`.
  Публичный интерфейс библиотеки не оперирует внутренними типами WinRT, то
  есть не требует подключения заголовков WinRT при сборке конечного
  приложения, благодаря чему оно собирается за секунды.
- **Истинное наследование и тонкие обёртки.** Классы обёрток в `wxl`
  наследуют друг друга так же, как их прототипы в **WinUI** (`wxl::Button` →
  `wxl::ButtonBase` → … → `wxl::UIElement`). Благодаря этому объект
  передаётся туда, где ожидается его базовый класс, нативными средствами
  языка и без приведений в духе `.as<T>()`. Сама обёртка представляет собой
  один умный указатель на скрытую цепочку реализации `Impl`. Ни один класс в
  публичной иерархии не добавляет собственных полей данных, поэтому размер
  любой обёртки всегда равен размеру одного указателя, а её копирование в
  базовый тип по значению абсолютно безопасно и не приводит к деструктивной
  срезке объектов (`object slicing`).
- **Декларативный DSL на чистом C++.** Дерево интерфейса описывается как
  единое выражение C++: свойства, вложенные элементы, пресеты (`Preset`),
  шаблоны (`Template`), обработчики событий и реактивные привязки (`Bind`)
  передаются в качестве аргументов конструктора и применяются к объекту в
  порядке записи. Передаваемые типы проверяет компилятор: неподходящий
  аргумент отвергается на этапе сборки с помощью `static_assert`, который
  выводит подсказку по исправлению. Благодаря `constexpr` и параметрам
  шаблонов константные пресеты и повторители элементов (по числу или
  строковому литералу) разворачиваются ещё при компиляции. Кроме того,
  события можно не только обрабатывать, но и нативно ожидать внутри корутин
  с помощью `co_await onClick(button)`.
- **Оптимизация под однопоточную модель (STA).** Интерфейс **WinUI** по
  спецификации работает в одном STA-потоке: объекты дерева интерфейса
  (элементы XAML, окна, визуалы композитора) вызываются только из потока, в
  котором созданы. Благодаря этому все внутренние сущности, которые `wxl`
  создаёт сама — объекты `Impl`, узлы событий и кадры корутин, — используют
  неатомарные счётчики ссылок и выделяются в пуле памяти потока
  (`sta_memory_pool`), свободном от блокировок и атомарных операций. Сами
  компоненты **WinUI** при этом остаются стандартными COM-объектами. Блокирующие
  операции (ввод-вывод, ожидания) делегируются рабочему потоку диспетчера
  `sta_loop`, а их результат возвращается в поток интерфейса, не останавливая
  его.
- **Инверсия управления точкой входа.** Функция `wWinMain` инкапсулирована
  внутри `wxl.ui`. Библиотека сама инициализирует среду выполнения Windows
  App Runtime, разворачивает STA-поток с его пулом памяти, создаёт объект
  приложения XAML и загружает ресурсы элементов управления — и лишь после
  этого передаёт управление в единственную прикладную функцию,
  `wxl_launched()`. В отличие от классической `main`, живущей всё время
  работы процесса, `wxl_launched()` реализует событийную модель запуска и
  остановки: её задача — декларативно описать окно и вернуть `Teardown`
  (обработчик завершения в виде функтора или лямбды; допустимо пустое
  значение, если не требуется специального обыгрывания завершения
  приложения). Библиотека сохраняет его и вызывает при закрытии приложения,
  передавая причину — штатное закрытие или сбой, — а результат обработчика
  становится кодом возврата процесса. Разработчику не нужно писать цикл
  сообщений, загрузчик или наследника `Application`, а все DLL среды
  выполнения копируются в выходную директорию приложения поставляемыми
  CMake-скриптами.

Подробный разбор архитектурных предпосылок и устройства генератора проекций
читайте в [первой статье цикла на Хабре](https://habr.com/ru/articles/1080690/).

## Примеры реализации

Ниже представлен фрагмент решения квадратного уравнения из
[samples/Quadratic/main.cpp](samples/Quadratic/main.cpp). Архитектура
построена на связывании реактивных контейнеров `observable` (бизнес-логика)
со свойствами интерфейса через декларативные привязки.

```cpp
class Equation : public noncopyable
{
    observable<Answer> answer;

public:
    observable<double> a{blank}, b{blank}, c{blank};
    observable<u16_text> D, x1, x2;

    Equation() {
        // Декларативное связывание: три числа на входе -> автоматический вызов solve
        answer
            .follow(a, b, c, solve)
            .on_change([this](Answer const& answer) noexcept {
                D.set(answer.D);
                x1.set(answer.x1); // Обновление состояния -> автоматическое отображение в UI
                x2.set(answer.x2);
            });
    }
};

// Пресет для унификации стилей ввода
const Preset input {
    common,
    width = 200,
};

// ... Инициализация элементов в декларативном дереве окна:
NumberBox {
    input,
    placeholderText = u"a",
    intermediateValue = BindInput {eq.a},
},
// ...
TextBox {
    output,
    text = BindOutput {eq.D},
},
```

Полный набор демонстрационных приложений (от калькулятора до комплексных
компонентов **WinUI** Gallery) с подробным описанием синтаксиса находится в
каталоге [samples/README.md](samples/README.md) и документе
[docs/dsl.md](docs/dsl.md).

## Быстрый старт

### Системные требования

Для сборки библиотеки и демонстрационных проектов вам понадобятся:

- **ОС:** Windows x64
- **Инструменты компиляции:** Visual Studio 2026 (канал Insiders) с тулсетом
  MSVC версии 14.53.36911 или новее
- **Средства WinUI:** в той же установке — рабочая нагрузка «WinUI application
  development» с компонентом «C++ WinUI app development tools»; в Build Tools
  для Visual Studio 2026 — рабочая нагрузка «WinUI application development
  build tools» с компонентом «C++ WinUI app development build tools». Пакеты
  NuGet и проекцию cppwinrt настройка получает от MSBuild этой установки
- **Windows SDK:** 10.0.26100.0 или новее
- **Сборка:** CMake (версии 4.3 / 4.4) и Ninja
- **Окружение:** PowerShell 7 (`pwsh`)

### Пошаговое развёртывание

Запустите сеанс `pwsh` из корневой директории склонированного репозитория и
выполните следующие команды для сборки дерева и запуска примера:

```powershell
# 1. Настройка и сборка всего дерева без сайта документации.
#    Настройка восстанавливает пакеты NuGet (закрепления — tools/packages.json,
#    результат — tools/packages.lock.json и список build\x64\wxl.packages\restored-packages.json)
#    и строит проекцию cppwinrt в каталоге сборки; сборка собирает генератор
#    winui-srcgen, пишет им обёртки WinUI полного профиля в build\x64\wxl.ui\full\wxl
#    и компилирует их вместе с остальным
tools\build.ps1 -Define WXL_BUILD_DOCS=OFF

# 2. Развёртывание экспериментальной среды выполнения Windows App Runtime
#    из пакета, который восстановила настройка
pwsh -NoProfile -File tools\install-runtime.ps1

# 3. Запуск демонстрационного приложения Quadratic
build\x64\samples\Quadratic\Debug\sample.quadratic.exe
```

Подробный разбор каждого шага автоматизации, поддерживаемые ключи
конфигурации CMake и запуск модульных тестов описаны в
[docs/building.md](docs/building.md). Собственный проект подключает корень
дерева `wxl` — `add_subdirectory` или `FetchContent` — и задаёт ключи языка
`wxl` до него (см. [«Подключение wxl»](docs/building.md#подключение-wxl)).

## Текущий статус и ограничения

Проект находится в стадии активной экспериментальной разработки. Обратная
совместимость между отдельными коммитами на данном этапе не гарантируется.
Портирование официальной
[WinUI Gallery](https://github.com/microsoft/WinUI-Gallery) выполнено по всем
группам элементов управления; не портированы лишь отдельные страницы, которым
нужны ещё не реализованные в **wxl** механизмы или пакеты вне профилей
(`SemanticZoom`, `WebView2`).

### Дефект оптимизатора MSVC (исправлен в тулсете 14.53.36911)

В тулсетах MSVC от 14.51 до сборки 14.53.36911 конфигурация **Release**
(`/O1` или `/O2` вместе с `/EHsc`) собиралась с дефектом: компилятор не
вызывал деструкторы локальных переменных корутины, у которой `final_suspend`
возвращает `std::suspend_never`, и не освобождал её кадр, если считал, что
тело корутины не бросает исключений. Тело `async::task`, которого никто не
ждёт, тоже заканчивается без приостановки, и дефект задевал и его; поскольку
завершение приложения ждёт, пока не останется живых кадров корутин,
демонстрационные примеры в `Release` могли зависнуть при закрытии окна.

В тулсете 14.53.36911 дефект исправлен: репро из отчёта под `/O2 /EHsc`, с
`/std:c++20` и с `/std:c++latest`, вызывает деструкторы и освобождает кадр
(проверено в октябре 2026 г.). Release снова собирается и проверяется
наравне с Debug.

- **На старых тулсетах** обход прежний: собирайте в конфигурации **Debug**,
  без оптимизации (`/Od`) или с асинхронной моделью исключений (`/EHa`).
  Подробный отчёт — [`bugs/coro-report.md`](bugs/coro-report.md).

### Ограничения кодогенерации

- **Состав профиля.** В **wxl** есть только те типы и члены **WinUI**, которые
  перечислены в профиле `wxl.gen/profiles/full.winxl-profile`. Чтобы
  добавить недостающее, профиль дополняют; следующая сборка генерирует
  обёртки сама.
- **Наследование с переопределением (Overrides).** Собственный наследник
  класса **WinUI** с переопределёнными методами через интерфейсы
  `I<Class>Overrides` пока не поддерживается: прототип агрегации
  COM-интерфейсов в `sandbox/Overrides` не собирается. В качестве временной
  альтернативы для своих контейнеров раскладки служат классы `CustomLayout`
  и `CustomVirtualizingLayout`.
