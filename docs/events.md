# События и привязки данных

## Обработчики событий

Подписка на события описывается декларативно через теги (например,
`onClick = …`). Лямбда-функция обработчика может принимать:

1. Только отправителя, типизированного его конкретным классом:
   `[](Button const& self) { … }`.
2. Отправителя и аргументы события:
   `[](Object const&, KeyRoutedEventArgs& args) { … }`.
3. Пустой список аргументов.

Сокращённая форма вида `onClick = {content = u"Thank You!"}` применяет
указанный набор аргументов непосредственно к отправителю события.

Тип аргументов события (например, `KeyRoutedEventArgs`) представляет собой
невладеющий и некопируемый вид (view) над ABI-указателем (`events.h`). Такая
архитектура исключает манипуляции со счётчиком ссылок и выделение памяти на
«горячем» пути исполнения (например, при непрерывной обработке перемещения
указателя мыши), а ограничение времени жизни аргументов рамками обработчика
контролируется компилятором. Обработчик намеренно не захватывает обёртку
собственного элемента управления — она извлекается из отправителя через
метод `try_as<T>()`.

## Асинхронное ожидание событий через `co_await`

Состояние, которое в классической императивной модели требовало бы
хранения множества флагов в сопутствующих обработчиках, внутри корутины
отображается на счётчик команд (`event_awaitable.h`). Пример из
демонстрационного проекта `samples/Gallery/Snippets/SplitButton/Text.h`:

```cpp
auto const hideOnClick = [](Flyout flyout, Button swatch) -> async::task<> {
    auto clicks = onClick(swatch);
    if (co_await clicks.next()) {
        flyout.hide();
    }
};

model->hiding.push_back(hideOnClick(flyout, swatch));   // задачи держит модель страницы
```

Конструкции вида `onClick(button)` или `on_event<EventKey::X>(element)`
создают объект подписки. Возобновление корутины выполняется самим
обработчиком непосредственно в точке вызова, что сохраняет контекст
выполнения и позволяет изменять состояние аргументов (например, вызывать
`args.handled(true)`) до фактического завершения системного события.

Ожидание прерывается и в отсутствие целевого события: при
удалении элемента из визуального дерева (`Unloaded`) или при завершении
работы приложения. В этих сценариях `co_await clicks` бросает исключение
`wxl::async::operation_canceled_exception`, тогда как `co_await clicks.next()`
возвращает пустое значение. Внешний токен отмены передаётся последним
необязательным аргументом: `onClick(button, stop)`. Подробнее об ожидании
событий в корутинах — [статья 3](https://habr.com/ru/articles/1085348/).

## Модель и механизмы привязки (Data Binding)

Поля прикладной модели данных типизируются контейнером
**`wxl::core::observable`** (`observable.ixx`), инкапсулирующим значение и
событие уведомления о его изменении. На этой основе реализованы следующие
компоненты:

- `observable<T const>` — то же поле, доступное только для чтения.
- `follow(источники…, функция)` — вычисляемое поле: значение формируется
  функцией из других полей и пересчитывается при их изменении.
- `on_change` — явная подписка на изменение состояния контейнера.
- `wxl::core::observable_list` — реактивный контейнер для списочных структур
  данных.

Объявление привязок данных (`Bind.h`) интегрируется непосредственно в
декларативное описание элементов управления:

- **`Bind{field}`** — двусторонняя привязка (Two-Way Binding). Компонент
  отображает текущее состояние поля модели, отслеживает его внешние
  изменения и автоматически записывает пользовательские правки обратно в
  модель. Применима только к тем свойствам, которые элемент управления
  способен изменять самостоятельно и о модификации которых он уведомляет
  штатными событиями (реестр пар зафиксирован в `binding.h`).
- **`BindOutput{field}`** — односторонняя привязка из модели в элемент
  управления (One-Way Binding). Допустима для любого свойства с публичным
  сеттером. Конструкция вида `itemsSource = BindOutput{list, build}`
  связывает компонент с контейнером `observable_list`, строя элемент
  интерфейса на каждый пункт данных. Вставка нового пункта в такую модель
  приводит к добавлению одной строки, а не к полному перестроению
  графического списка.
- **`BindInput{field}`** — односторонняя привязка из элемента управления в
  модель. Применяется, например, в сценарии `intermediateValue =
  BindInput{eq.a}` для компонента `NumberBox`: число записывается в том
  виде, в каком оно набрано, при каждом нажатии клавиши.

Направление потока данных проверяется на этапе компиляции. Если свойство
поддерживает только отображение данных, использование `Bind` будет
отвергнуто компилятором с подсказкой о необходимости перейти на
`BindOutput`. Безымянная инициализация вида `Bind{field}` автоматически
выбирает основное свойство компонента по совпадению типов (например,
связывает `observable<bool>` со свойством `isOn` элемента `ToggleSwitch`).

## Границы применимости и управление жизненным циклом

Объект привязки оперирует прямым адресом поля модели и не управляет
временем его жизни, тогда как внутренняя подписка поля владеет обёрткой
элемента управления. Прикладная модель обязана пережить ассоциированные с
ней привязки интерфейса. В демонстрационном проекте `samples/Quadratic`
жизнь модели продлевается за счёт её захвата в обработчик `wxl::Teardown`.

Если время жизни модели превышает жизненный цикл графического окна,
разработчик обязан явно разорвать связи при закрытии окна (вызовами
`unbind()` или `unsubscribe_all(…)`), в противном случае поля модели будут
удерживать элементы управления закрытого окна.
