# Форматирование текста: область `fmt`

Собственный буфер и построитель текста поверх библиотеки
[fmt](https://github.com/fmtlib/fmt): компоненты `text_buffer` и
`text_builder` и функция `format` — текст для интерфейса одним вызовом.
Это область `fmt` модуля `wxl.core` (`wxl.core/src/fmt`): подключение —
`import wxl.core;`, цель сборки — `wxl::core`.

```cpp
import wxl.core;

wxl::core::text_builder<> out;

out.format("{}: страница {} из {}", title, page + 1, count);
out.append(" — ");
out.format("{:.0f}%"_cf, share * 100.0);   // using namespace fmt::literals

write(out.view());

u16_text text = format(u"{:.9g}", root);   // double или std::complex<double> — девять цифр у каждой части
```

## Ключевые архитектурные решения

- **Почему `fmt`, а не `std::format`.** Построителю необходим прямой вывод в
  целевой буфер без промежуточных шагов. Стандартный `std::format` такой
  точки расширения не предоставляет и выполняет двойную работу: `format_to`
  с итератором `back_inserter` разбивает вывод на посимвольные `push_back`,
  `format_to_n` использует внутренний буфер на стеке с последующим
  копированием, а `formatted_size` требует второго полного прохода по данным
  — сначала измерить длину, потом форматировать. Библиотека `fmt` изначально
  спроектирована вокруг буфера (`fmt::basic_memory_buffer`) и форматирует в
  предоставленный буфер за один проход; `text_buffer` — её буфер,
  адаптированный под аллокаторы **wxl**.
- **`fmt` — зависимость ядра.** Библиотека `fmt` — единственная сторонняя
  зависимость модуля `wxl.core`, и цель `wxl::core` подключает её модуль
  публично: `text_buffer` — это `fmt::basic_memory_buffer`, а
  `text_builder::format()` — шаблон, который инстанцируется у вызывающего,
  поэтому всякий, кто компилирует интерфейсы `wxl.core`, компилирует их
  вместе с модулем `fmt`.
- **Пространство имён `wxl::core`.** Буфер и построитель — часть ядра, и их
  имена лежат в его пространстве имён:
  `wxl::core::text_builder<sta_allocator>`.

## `text_builder`: сборка текста по частям

**Разделение `format` и `append`.** Форматирование (`format`) и дописывание
обычного текста (`append`) разнесены по разным методам намеренно. Форматная
строка и произвольный текстовый блок имеют разную семантику: фигурная
скобка в первом случае — синтаксический элемент, во втором — обычный
символ. Поскольку `format()` вызывает разбор форматной строки, а `append()`
выполняет прямое копирование памяти, символы `{` и `}` внутри произвольного
текста (например, имени файла) никогда не приведут к ошибке разбора во
время выполнения.

**Выбор аллокатора.** По аналогии с функцией `try_parse` в ядре библиотеки,
`text_builder` параметризуется аллокатором на уровне шаблона класса:
`text_builder<wxl::core::sta_allocator>` размещает внутренний буфер в
однопоточном пуле STA и предназначен для потока графического интерфейса;
по умолчанию (`text_builder<>`) используется обычная системная куча
процесса — для потоков, в которых пул STA не инициализирован.

**Замер: свой буфер против `fmt::basic_memory_buffer`.** Поскольку пул памяти
**wxl** выделяет блоки сдвигом линейного курсора, блок, выданный последним,
теоретически мог бы расширяться на месте без перемещения, и тогда буфер
при росте никогда не копировал бы сам себя. На практике этот сценарий почти
не наступает: если пул уже активно использовался приложением, в нём
преобладают списки свободных блоков, где у каждого блока есть фиксированный
сосед позади, и сдвиг курсора оказывается эффективен только для самого
первого буфера за время жизни программы. Бенчмарк
(`wxl.core/benchmarks/fmt/text_builder_benchmark.cpp`, конфигурация `Release`) на
20 000 последовательных записей в один буфер показал: собственная
реализация буфера поверх пула — 180 мс, готовый `fmt::basic_memory_buffer` с
тем же аллокатором — 167 мс.

**`_cf`: разбор форматной строки на этапе компиляции.** Независимо от выбора
буфера форматную строку можно разобрать на этапе компиляции с помощью
литерала `"…"_cf` из `fmt::literals` (в заголовках `fmt` это макрос
`FMT_COMPILE`, но макросы через модуль не проходят). Поскольку разбор
строки не зависит от способа управления памятью, `_cf` сочетается с любым
буфером: тот же прогон на `fmt::basic_memory_buffer`, но с разбором строки на
этапе компиляции, занимает 113 мс вместо 167 мс. Это две независимые оси
оптимизации: стратегия памяти выбирается один раз при объявлении класса
`text_builder`, а `_cf` применяется точечно для конкретных форматных строк —
внутри циклов и на горячих путях выполнения.

## `format`: проверенный текст одним вызовом

Построитель собирает текст по частям в свой буфер; `format` предназначена
для другого случая, когда нужна одна строка для элемента управления:
`format(u"{:.9g}", root)` возвращает `u16_text`; `root` здесь — `double` или
`std::complex<double>`, и спецификация одна на обе части: `(-1+2i)`.
Форматтер для `std::complex` собственный, в `format.ixx`, и берёт верх над
форматтером из `fmt/std.h` как более ограниченный: тот при нулевой
вещественной части печатает `2.5i`, этот всегда `(re+imi)`.

Корректность результата держится на ограничении аргументов, а не на
проверке: числа дают ASCII, `u16_view` и `u16_text` уже проверены, и ничего
другого функция не принимает — непроверенный `std::u16string_view` или
одиночный `char16_t` отвергаются концептом, потому что внесли бы в результат
текст неизвестной корректности; текст извне сначала проходит `checked()`.
Форматная строка — литерал, проверенный `fmt` на этапе компиляции, или
`u"…"_cf`. Внутри — `fmt::basic_memory_buffer<char16_t>` на 256 единиц в
стеке и одна копия в строку результата; для литерала разбор и запись
выполняются в `format.cpp` через `basic_format_args`, так что шаблон в
вызывающем коде — только упаковка аргументов.

## `fmt` — модуль, собранный из исходников

Область `fmt` пишет `import fmt;`, и `fmt` для этого собирается модулем из
собственных исходников. Заголовки `fmt` в глобальном фрагменте модуля рядом
с `import std;` MSVC совмещает со стандартной библиотекой через обходной
приём (`extern "C++"` вокруг заголовков STL), который не дотягивается до
явных специализаций (`<stop_token>` из `<thread>`) и до частичных
специализаций с зависимыми выражениями (`is_back_insert_iterator` на пути
`filesystem::path` из `fmt/std.h`). Модулю, который сам выполняет
`import std;` (`FMT_IMPORT_STD`), совмещать нечего, и `fmt/std.h` вместе с
`chrono.h` и `ranges.h` подключаются штатно.

`fmt` собирается в `wxl.core/src/CMakeLists.txt` из собственных исходников
(`FetchContent`; порт vcpkg модуля не предоставляет), а не его сценарием
CMake: тот создаёт цель-модуль только для генератора «Ninja», тогда как
дерево **wxl** использует Ninja Multi-Config. Модульная единица — копия
`src/fmt.cc` без `format.cc` рядом: иначе определения dragonbox попадают в
модуль, импортёр инстанцирует их сам вместо готовых экземпляров, а MSVC
14.51 при этом теряет параметр шаблона, прочитанного из модуля. `format.cc`
компилируется обычной единицей той же библиотеки, а модуль привязывает свои
объявления к глобальному модулю (`FMT_ATTACH_TO_GLOBAL_MODULE`), чтобы имена
совпали при компоновке.
