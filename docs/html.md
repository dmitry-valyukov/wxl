# `wxl.html`: подмножество HTML для `RichTextBlock`

## Назначение

Модуль наполняет `RichTextBlock` форматированным содержимым (сообщением
форума, лентой чата, справкой) декларативно и без WebView. HTML здесь
служит форматом *входных данных*, зачастую сторонних и некорректных, а не
языком вёрстки приложения: парсер обязан обработать любой мусор и извлечь
из него наилучший возможный текст.

HTML — не единственный такой формат. Форумы, к которым имеет смысл
подключаться, отдают JSON, XML, BB- или RSDN-разметку в плоском тексте
(в `style="color: ..."` их превращает сайт или локальный клиент, например
Janus для КЫВТ). **Принято**: каждая разметка получает собственный контрол
со своим парсером, а общая часть выносится в базовый класс.

## Семейство: `FormattedBlock` и наследники

Системный `RichTextBlock` запечатан, однако наследование в wxl.ui
реализовано на уровне обёрток: классы проекции не имеют ни одного поля, а
состояние хранится в цепочке `Impl`, созданной через `make<T>`. Под
обёрткой остаётся тот же WinRT-объект `RichTextBlock`.

- **`wxl::FormattedBlock : RichTextBlock`** содержит примитивные операции
  наполнения, общие для всех разметок: добавление спана заданным шрифтом и
  цветом, стек стилей, ссылки, картинки, встроенные элементы. Черновой
  набор:
  - начать блок (отступы `Margin`, выравнивание) и закончить блок;
  - стек строчных стилей: push/pop (шрифт, кегль, жирность, курсив,
    подчёркивание, зачёркивание, цвет);
  - добавить текст текущим стилем; добавить перенос строки;
  - добавить ссылку (текст и идентификатор передаются общему обработчику
    `onLink`);
  - добавить картинку (источник, размеры, подсказка);
  - добавить произвольный `UIElement` (`InlineUIContainer`);
  - очистить содержимое; место вставки для дописывания также хранится
    здесь.
- **`wxl::MarkupBlock : FormattedBlock`** — общий уровень контролов
  разметки, выделенный, когда родственные контролы появились на практике.
  Он содержит тему (`wxl::MarkupTheme`), каталог картинок `baseDirectory()`,
  реестр именованных стилей и общий сборщик, который обходит дерево
  семейства (`MarkupBlock.cpp`).
- **`wxl::HtmlBlock : MarkupBlock`** — парсер HTML-подмножества поверх этих
  примитивов. **Контролы `wxl::BbBlock` и `wxl::RsdnBlock` стоят рядом с
  ним** (**сделано**): собственные у них только токенизаторы — модули
  `wxl.bb` и `wxl.rsdn`, которые строят то же дерево через
  `wxl::html::tree_builder` (`wxl.html:builder`). Стек, автозакрытие,
  восстановление по образцу браузеров, обработка пробелов и терминированные
  виды у них общие с HTML и отлажены один раз. Отличия описаны в самих
  модулях: в форумных разметках значим перевод строки, незнакомый тег
  остаётся буквальным текстом, сущностей нет. RSDN добавляет построчные
  цитаты (строки вида «AVK> так и было» складываются в blockquote с видимым
  префиксом, а число стрелок задаёт вложенность), языковые теги кода
  (`[c#]`, `[nemerle]`…) с подсветкой через `wxl.highlight` (фрагменты кода
  размечаются как `<span style="kw">`, `"str"`, `"com"`), смайлы форума в
  виде картинок и адреса непосредственно в тексте.

Предполагаемый способ использования:

```cpp
HtmlBlock {
    html = L"Привет, <b>мир</b>! Подробности <a href='faq'>тут</a>.",
    onLink = [](std::wstring_view href) { ... },
}
```

Над содержимым определены две операции, обе доступны после построения:

- **Замена**: присваивание `html` полностью заменяет `Blocks()`.
- **Дописывание**: содержимое добавляется в конец без перестройки
  существующего (**принято**: лента чата дополняется, а не пересоздаётся;
  полная замена на каждое сообщение соответствует подходу WebView, от
  которого модуль отказывается).
  **Принято**: семантика не ограничивается правилом «всегда новый абзац»:
  строчное содержимое продолжает последний абзац, а блочные теги
  открывают новые.
- **Принято для DSL**: декларативная запись только создаёт контрол, и в
  ней используется присваивание `html = ...`. Дописывание выполняется
  обычными процедурными методами `append*()` обёртки.
- **Главное правило процедурной вставки (принято)**: каждая вставка
  закрывает все блоки; если вход по ошибке их не закрыл, они закрываются
  принудительно. Причина: между вставками не хранится ни исходный HTML, ни
  состояние парсера, и при поступлении содержимого частями ничто не
  разбирается заново. Каждый фрагмент самодостаточен: незакрытый `<b>` не
  переходит в следующий `append`.

Текст без блочных тегов помещается в неявный `Paragraph`: сообщение чата
«просто текст с `<b>`» должно работать без дополнительной обвязки.

## Кодировка входа

Поддерживаются два явных входа; тип входа не угадывается:

- `std::wstring_view` — широкая строка, непосредственный вход
  (литералы DSL, текст от Windows);
- `wxl::core::u8_view` — уже проверенный UTF-8 (текст, прошедший через
  `wxl::core`, например принятый из сети и проверенный на верхнем уровне).

**Принято** в таком виде: широкая строка принимается непосредственно, а
`u8_view` — собственный тип **wxl** с проверенным содержимым.

## Слои внутри `HtmlBlock`

- **Ядро** включает токенизатор, сущности, нормализацию пробелов и
  восстановление после ошибок; его результат — **собственный легковесный
  DOM** (**принято**). Ядро написано на чистом C++ без зависимостей от
  **WinUI** и проверяется обычными тестами wxl: HTML на входе,
  сериализованный DOM на выходе, сравнение с эталоном (golden).
- **Сборщик** обходит DOM и вызывает примитивы `FormattedBlock`. Правило
  границы то же, что во всей библиотеке: `winrt::` за её пределы не
  выходит.

DOM здесь — рабочая структура одного вызова, а не хранилище: он строится,
обходится и удаляется (см. правило вставки: ни HTML, ни DOM между
вызовами не сохраняются). DOM нужен потому, что восстановление
вложенности, нормализация пробелов и golden-тесты — операции над деревом,
а не над потоком токенов.

**Хранение DOM — по образцу `wxl.xml`** (**принято**): арена блоками из
STA-пула, дети — `wxl::core::intrusive_slist` через поле в самом узле,
один конкретный тип узла с дискриминатором `tag_t` вместо иерархии с vptr, атрибуты —
`std::span` в арене; ни одного лишнего STL-контейнера на узел. Отличие
одно: wxl.xml выдаёт виды на исходный буфер, а HTML-текст после разбора
сущностей и схлопывания пробелов не равен исходному. Этот случай арена
также поддерживает: `tree_builder::copy` возвращает вид на собственную копию.

Ядро **не использует `wxl.xml`**: форумный HTML на практике не является
well-formed (`<br>` без закрытия, `&nbsp;`, кавычки в произвольных
местах), а `wxl.xml` по замыслу отвергает такой документ целиком.
Толерантность к ошибкам — требование, а не уступка.

## Теги первой очереди

Блочные теги (у `Block` есть `Margin`, `TextAlignment`, `LineHeight`,
поэтому отступы и выравнивание абзацев реализуются полноценно):

| Тег | Во что | Примечание |
|---|---|---|
| `<p>` | `Paragraph` с вертикальным `Margin` из `wxl::MarkupTheme` | |
| `<div>` | `Paragraph` без отступов | только граница блока; вложенные `<div>` разворачиваются в плоскую последовательность абзацев, стили наследуются вниз |
| `<br>` | `LineBreak` | |
| `<h1>`–`<h3>` | `Paragraph` + кегль и жирность из стилей | масштабы задаются в `MarkupTheme` |
| `<blockquote>` | `Paragraph` с левым `Margin` + вторичный цвет | фона и рамки у `Paragraph` нет; вертикальную полосу при необходимости может дать только `TextHighlighter` (вторая очередь) или элемент в контейнере |
| `<ul>/<ol>/<li>` | `Paragraph` на пункт: «• » / «1. », висячий отступ левым `Margin` + отрицательным `TextIndent` | вложенность выражается увеличением левого `Margin` |
| `<pre>` | `Paragraph` моноширинным шрифтом; `\n` → `LineBreak`; пробелы сохраняются | перенос строк отключить нельзя; ограничение принято |

Строчные теги:

| Тег | Во что |
|---|---|
| `<b>/<strong>` | `Bold` |
| `<i>/<em>` | `Italic` |
| `<u>` | `Underline` |
| `<s>/<del>` | `Span` + `TextDecorations::Strikethrough` |
| `<code>` | `Run` моноширинным шрифтом |
| `<a href>` | `Hyperlink` |
| `<img>` | `InlineUIContainer` + `Image` (GIF анимируется самостоятельно) |
| `<sub>/<sup>` | `InlineUIContainer` + уменьшенный `TextBlock` со сдвигом: путь через OpenType (`Typography.Variants`) для произвольных букв не работает, а вертикального сдвига у `Run` нет |
| `<font>` | `Span` с цветом, шрифтом и кеглем — **принято: в первой очереди** |

Вторая очередь (**сделано**): `<hr>` — полоса толщиной в линию во всю
ширину текста; `<table>` — см. отдельный раздел; `<details>` со
`<summary>` — раскрывающийся блок: `Expander` без содержимого служит
заголовком, а содержимое — абзацы того же блока, которые складка скрывает
и показывает на месте (`beginFold`/`endFold` у `FormattedBlock`). Поэтому
ничего не вкладывается, и выделение проходит сквозь складку. Все три
элемента являются «широкими элементами» (`appendWideElement`): пока блок
переносит текст, они получают ширину текстовой области и следуют за ней
при изменении размера (это ширина, которую браузер даёт блочному боксу);
при `TextWrapping::NoWrap` они сохраняют естественную ширину, как и
строки.

Ещё не реализованы: `<mark>` через `TextHighlighter` и фоновая плашка
`<code>` тем же механизмом.

Сознательно не поддерживаются: CSS как язык — селекторы, каскад, разбор
деклараций (атрибут `style` поддержан, но его значение — имя
зарегистрированного стиля, см. «Именованные стили»; реальные источники
отдают BB/RSDN/JSON, а CSS в `style` порождают сторонние сайты и клиенты,
а не **wxl**), скрипты, формы.

## Атрибуты

- `<a>`: `href`.
- `<img>`: `src`, `width`, `height`, `alt`. Размеры **обязательны**:
  картинка загружается асинхронно, и без явного размера строка смещается
  после загрузки. `alt` передаётся в `toolTip` и служит одновременно
  подсказкой и именем для экранного диктора.
- `<font>`: **принято**
  - `color` — `#rgb` / `#rrggbb` / именованный цвет, полный набор из
    ~140 CSS-имён (это наиболее дешёвый вариант: одна таблица);
  - `face` — имя семейства; из списка через запятую берётся первое;
  - `size` — **семантика та же, что у HTML**: шкала `1`–`7` (по
    умолчанию 3) и относительные `+n`/`-n`; значения отображаются в
    множители базового кегля.

## Сущности

Поддерживаются пять сущностей XML (`amp lt gt quot apos`), числовые
`&#...;` / `&#x...;` и короткий список именованных:
`nbsp mdash ndash laquo raquo hellip copy`. **Принято**: полный набор именованных
сущностей HTML не нужен. Незнакомая сущность остаётся литеральным текстом.

## Пробелы

Пробелы обрабатываются по правилам HTML: цепочки пробельных символов
схлопываются в один пробел, на границах блоков обрезаются, пробельный
текст между блочными тегами отбрасывается; `<pre>` сохраняет всё. Этот
раздел тестов ядра — самый крупный.

## Ошибки разметки: текст сохраняется, теги — нет

Содержимое поступает из сторонних источников, поэтому парсер **никогда не
выбрасывает исключений на некорректный вход**. Из любого мусора на входе
извлекается наилучший возможный текст.

- Незнакомый тег отбрасывается, а его содержимое остаётся текстом (как в
  браузерах).
- **Нарушенная вложенность обрабатывается по образцу браузеров**
  (упрощённый вариант их adoption agency algorithm). **Принято** на примере
  `<b>first<i>second</b>third</i>`: `first` — жирный, `second` — жирный
  курсив, `third` — курсив. Иначе говоря, закрывающий тег закрывает свой
  элемент, а форматирующие элементы, открытые внутри него, открываются
  заново следом и продолжают действовать.
- Блочный тег внутри строчного принудительно закрывает строчные.
- Закрывающий тег без соответствующего открытого игнорируется.
- Одиночный `<`, не начинающий тег, считается обычным символом.

## Ссылки

Один обработчик `onLink` обслуживает весь блок (он хранится в
`FormattedBlock`). Если обработчик задан, каждый щелчок передаётся ему
(сноски, внутренняя навигация). Если он не задан, ссылки `http`/`https`
открываются браузером, а остальные схемы блокируются: для читателя без
уведомления, для `onError` — с записью `BlockedLink`. Ссылки
`javascript:` и `file:` в стороннем содержимом — реальная, а не
гипотетическая угроза.

Элементы, которые `Hyperlink` не может содержать (перенос строки,
картинку, `sub`/`sup`), ссылка **обходит расщеплением**: элемент
размещается между двумя половинами с одной целью, порядок текста
сохраняется, обе половины остаются кликабельными.

## Картинки

**Принято: только локальные источники** — голый путь, `file://`,
`ms-appx://`, `ms-appdata://`. Остальные схемы отбрасываются с записью
`RemoteImage` в `onError`. На будущее обсуждается событие вида «request
image/video»: парсер встречает внешний источник и запрашивает у
приложения содержимое для него. Это запланировано и в первую очередь не
входит.

Относительный путь разрешается от каталога, заданного
`HtmlBlock::baseDirectory()`; для разметки из файла это каталог файла.
Если каталог не задан, путь разрешается от рабочего каталога процесса
(ресурсы приложения). Картинка, которая не загрузилась (файл отсутствует,
формат повреждён), обнаруживается асинхронно и передаётся записью
`ImageFailed` в тот же `onError`.

## Диагностика: `onError`

Один приёмник обслуживает весь блок; он хранится в `FormattedBlock` рядом
с `onLink`. Каждое восстановление, которое стек по замыслу выполняет без
уведомления, оставляет запись `wxl::MarkupError{kind, detail}`: незнакомый
тег, непарный закрывающий тег, нарушенная вложенность, некорректная
сущность, незнакомое имя стиля, некорректные цвет, кегль или размер,
картинка без источника или с удалённым источником, заблокированный щелчок.
Ни одна из этих ситуаций не является ошибкой выполнения, поскольку текст
сохраняется всегда; запись нужна разработчику, который не видит на экране
того, что написал в разметке.

Поле `detail` называет источник проблемы (имя тега, тело сущности,
значение атрибута) и действительно только внутри вызова обработчика, как
вид в аргументах события. Записи построения приходят синхронно из
`html()`/`append()` (записи парсера — первыми, в порядке входа), а
`ImageFailed` и `BlockedLink` — позже, из потока интерфейса. Одиночный `&`
без `;` записи не создаёт: «Tom & Jerry» — обычный текст, а не
повреждённая сущность. Парсер накапливает свои записи в
`wxl::html::document::errors()` с ограничением в несколько десятков:
враждебный вход повторяет один и тот же мусор, а диагностике нужна форма
проблемы, а не каждый её экземпляр.

## Таблицы

**Сделано** по этому же предложению. Носителем служит `Grid` в
`InlineUIContainer`, размещённом отдельным абзацем; собственных таблиц у
`RichTextBlock` нет. Соответствие прямое:

- `<table>` → `Grid` в рамке `Border` (левая и верхняя линии принадлежат
  рамке, правая и нижняя — каждой ячейке, поэтому каждая линия рисуется
  один раз; кисть — `tableBorderColor` темы, а при пустом поле —
  разделитель темы окна);
- `<tr>` → строка, `<td>`/`<th>` → ячейка: `Border` с `cellPadding` и
  вложенным `FormattedBlock`, поэтому в ячейке работают все теги первой
  очереди и второй тоже (вложенность таблиц допускается до восьми
  уровней, глубже содержимое выводится плоско); `<th>` выводится жирным и
  по центру; ссылки и диагностика ячеек передаются в обработчики
  корневого блока;
- `colspan`/`rowspan` → `Grid.ColumnSpan`/`RowSpan` один в один, с
  раскладкой, которая сдвигает ячейки под объединённой ячейкой сверху;
- ширины вычисляются по основному алгоритму автоматической раскладки
  браузера: у колонки две ширины, max-content (самая широкая ячейка,
  измеренная без ограничения) и min-content (самое длинное неразрывное
  слово; ячейка измеряется нулевой шириной). Если таблица помещается по
  max, колонки получают ширину `auto`; иначе излишек над суммой min
  распределяется между колонками пропорционально запасу max − min в
  пикселях, и ни одна колонка не становится уже своего слова. Пересчёт
  выполняется при каждом изменении ширины полосы. Без переноса текста
  полоса не ограничена, и таблица сохраняет естественную ширину; линейка
  при этом всегда занимает всю строку, поскольку собственной ширины у неё
  нет.

Дерево не читает атрибут `width` у колонок и ячеек; поддержка вернётся,
если её запросит реальный потребитель.

Ограничения:

- выделение текста не пересекает границу таблицы, поскольку содержимое
  ячеек находится в собственных `RichTextBlock`; это единственное место
  семейства, где содержимое вложено, и другого носителя для строк и
  колонок нет;
- таблица не разрывается между колонками `RichTextBlockOverflow`.

**Решение бывшего главного риска.** `InlineUIContainer` измеряет дочерний
элемент шириной строки, но размещает его по желаемой ширине: пустой
`Border` схлопывается до нуля, а `Grid` с колонками `auto` измеряет ячейки
бесконечной шириной и не может определить, помещается ли он. Поэтому
широкие элементы получают ширину явно — от блока по его событию
`SizeChanged`, а не от контейнера. Для браузера этот вопрос не возникает:
там блочная вёрстка первична, и блочный бокс по определению получает
ширину содержащего блока; здесь первичен текст, и ширину блочному
элементу приходится передавать явно.

## Именованные стили: `style` без каскада

**Принято.** Атрибут `style` поддерживается, но его значение — не CSS, а
имя заранее зарегистрированного стиля: `<div style="quote">`. Каскад,
селекторы и разбор деклараций не используются; стиль находится прямым
поиском по имени.

- Объект `MarkupStyle` содержит и строчные грани (те же, что
  `wxl::TextStyle`: шрифт, кегль, жирность, курсив, подчёркивание,
  зачёркивание, цвет), и блочные (отступы, выравнивание). Блочный тег
  использует все грани, строчный — только строчные.
- Регистрация выполняется методами `HtmlBlock`:
  - `registerStyle(имя, MarkupStyle)` — один стиль;
  - `registerStyles({{имя, стиль}, {имя, стиль}, ...})` — группа пар
    «ключ — значение» одним вызовом (`initializer_list` пар).
- Стиль действует на элемент и его содержимое по тому же механизму, что и
  стек строчных стилей; это наследование по вложенности, а не каскад
  правил.
- **Принято: одно имя на элемент.** Поддержка нескольких имён через
  пробел (как у `class`) вернётся, только если её запросит реальный
  потребитель.
- Незнакомое имя игнорируется: в `style` стороннего HTML находится
  настоящий CSS (`color: red`), и он должен просто не найтись, а не
  прервать разбор. Собственное имя с опечаткой выглядело бы так же,
  поэтому незнакомое имя передаётся записью в `onError` (см.
  «Диагностика»).

## Тема

**Принято и сделано**: `MarkupTheme` (имя выбрано так, чтобы не совпадать с
`MarkupStyle` именованных стилей) — объект со значениями оформления: отступы
`<p>`, заголовков, цитаты и `<pre>`, масштабы `h1`–`h3`, цвет цитаты,
моноширинная гарнитура, отступ пункта списка, геометрия `sub`/`sup`,
сторона картинки без размеров. Значения по умолчанию воспроизводят вид
первой очереди без изменений. `HtmlBlock::theme()` заменяет объект
целиком и действует на всё, что строится после вызова (уже построенное
содержимое сохраняет оформление, с которым оно строилось, как и в случае
именованных стилей).

Цвета в теме необязательны: пустое поле берётся из ресурса темы окна в
момент построения (цвет цитаты — из `TextFillColorSecondaryBrush` через
механизм `brushes.*`), так что тёмная и светлая темы получают каждая свой
цвет. Выражать тему зарезервированными именами реестра стилей
(бывший открытый вопрос) не стали: у темы есть грани, которых нет у
`MarkupStyle` (масштабы, гарнитура `<pre>`, сторона картинки), и один
цельный объект точнее набора разрозненных имён.

## Профиль генератора

Профилю нужен только сам `RichTextBlock` (в `base.json`, рядом с
`TextBlock`). Семейство `Documents` — `Paragraph`, `Run`, `Hyperlink` и
другие классы — в профиль **не входит**: наполнение выполняется через
примитивы `FormattedBlock`, а их реализация получает `Documents` из
проекции cppwinrt внутри библиотеки, где `winrt::` допустим. Публичные
обёртки эти классы не получают, пока кто-либо извне не запросит их по
имени.

## Закрытые вопросы

Таблицы — **сделаны** (см. «Таблицы», там же решение бывшего главного
риска с измерением `InlineUIContainer`); несколько имён в `style` — **одно имя** (см.
«Именованные стили»); тема реестром — **нет, объект `MarkupTheme`** (см.
«Тема»); базовый каталог картинок — **сделан**,
`HtmlBlock::baseDirectory()` (см. «Картинки»).

Список примитивов `FormattedBlock` больше не является открытым вопросом:
он выверен сборщиком. К первому набору добавились
`appendParagraph(BlockStyle)`, `pushLink`/`popLink` и `appendScript`;
актуальный перечень приведён в `FormattedBlock.h`.
