# Сборка и верификация

## Требования

Всё дерево представляет собой единый проект CMake, и почти весь код в нём
реализован в виде модулей C++20 с использованием `import std;`. Это
накладывает следующие требования к инструментарию:

- **Операционная система:** Windows x64.
- **Процессор:** x64 с инструкцией `lzcnt` (Intel Haswell и новее, AMD с
  2007 года): индекс класса размера в `sta_memory_pool` — сама инструкция через
  интринсик, и пул отвергает процессор без неё при старте. Ключей `/arch` в
  дереве нет: под `/arch:AVX` MSVC 14.53 не компилирует корутину с
  симметричной передачей, переносящую 32-байтный объект (ошибка C4737).
- **Ключ `/Zc:throwingNew`:** его задаёт `cmake/config.cmake` на всё дерево.
  Ключ сообщает компилятору, что функции выделения памяти следуют стандарту:
  функция, объявленная без `noexcept`, нуля не возвращает. Пул
  `wxl::core::sta_memory_pool` нуля не возвращает тоже: при нехватке памяти
  он завершает процесс. MSVC 14.53.36911 по этому ключу убирает проверку на
  ноль только после глобального `operator new`; после собственного
  `operator new` класса, в том числе выделяющего память из пула, проверка
  остаётся, что видно по листингу компилятора. Ключ оставлен, чтобы
  намерение было записано: компилятор, который учтёт его и для собственных
  функций выделения памяти классов, уберёт эти проверки без правок в дереве.
  На всё дерево, а не как требование цели `wxl::core`: CMake сравнивает
  опции компиляции потребителя с опциями цели модуля `std` и при расхождении
  синтезирует для потребителя свою копию модуля. У `wxl::core` есть ещё ключ
  `/Gw`, только в Release, и с `/Zc:throwingNew` на цели её потребители
  расходились бы с модулем в обеих конфигурациях, причём по-разному. CMake
  4.4.1–4.4.4 в генераторе Ninja Multi-Config делает копии для Debug и
  Release зависимыми друг от друга и останавливает генерацию на этом цикле.
  Ключ на всё дерево попадает и в цель модуля: в Debug потребители берут
  модуль как есть, и копия остаётся одна, для Release. В свой проект этот
  ключ добавлять не нужно.
- **Компилятор:** Visual Studio 2026 (канал Insiders) с поддержкой C++ и
  набором инструментов MSVC версии 14.53.36911 или новее; он необходим для
  работы `import std;` в модулях C++20, а более ранние сборки тулсета собирают
  Release с дефектом корутин (см. «Release и дефект MSVC»).
- **Средства WinUI:** в той же установке Visual Studio 2026 — рабочая нагрузка
  «WinUI application development» (`Microsoft.VisualStudio.Workload.Universal`)
  с компонентом «C++ WinUI app development tools»
  (`Microsoft.VisualStudio.Component.WindowsAppSdkSupport.Cpp`); в Build Tools
  для Visual Studio 2026 — рабочая нагрузка «WinUI application development
  build tools» (`Microsoft.VisualStudio.Workload.UniversalBuildTools`) с
  компонентом «C++ WinUI app development build tools»
  (`Microsoft.VisualStudio.ComponentGroup.WindowsAppDevelopment.VC.BuildTools`).
  Пакеты NuGet и проекцию cppwinrt настройка получает от MSBuild этой
  установки (см. «Пакеты NuGet и проекция cppwinrt»). Если компонента нет,
  настройка останавливается и называет, что установить.
- **Windows SDK:** версии 10.0.26100.0 или новее (компонент установщика
  `Microsoft.VisualStudio.Component.Windows11SDK.26100`). Сборка берёт
  новейший установленный SDK, который выбирает окружение разработчика, и
  одна и та же версия идёт в проекцию и в компиляцию. Если она ниже
  10.0.26100.0, настройка останавливается.
- **Система сборки:** CMake версии 4.3 или 4.4. Нижняя граница задана в
  конфигурации как `cmake_minimum_required(VERSION 4.3)`. Верхнюю границу
  определяет UUID-ключ механизма `import std;`: сценарию
  `cmake/wxl_import_std_gate.cmake` эти ключи известны для версий 4.1–4.4.
- **Генератор:** Ninja. Генераторы Visual Studio не строят BMI
  (скомпилированные интерфейсы модулей) для импортированных целей.
- **Командная оболочка:** PowerShell 7 (`pwsh`).
- **Сетевое подключение:** необходимо при первой настройке для загрузки
  пакетов NuGet, зависимостей `winmd` и `fmt` через механизм `FetchContent`
  (при `BUILD_TESTING=ON` — и GoogleTest), а также Doxygen 1.18 и темы
  оформления сайта документации.

## От клона до окна

Проекция `cppwinrt` и декларативные обёртки `wxl` в репозиторий не входят:
проекцию строит настройка дерева в каталоге сборки, обёртки — шаг самой
сборки. Чтобы собрать дерево и запустить первое приложение, выполните в среде
`pwsh` из корня дерева следующие команды:

```powershell
tools\build.ps1 -Define WXL_BUILD_DOCS=OFF       # настройка (пакеты NuGet, проекция) и сборка, обёртки — её шаг
pwsh -NoProfile -File tools\install-runtime.ps1  # экспериментальная среда Windows App Runtime
build\x64\samples\Quadratic\Debug\sample.quadratic.exe
```

- **Экспериментальный канал:** дерево собирается по одному выпуску
  Windows App SDK — зонтичному пакету `Microsoft.WindowsAppSDK` в
  `tools/packages.json`; версии входящих в него пакетов объявляет сам
  выпуск. Это выпуск экспериментального канала, поскольку в метаданных
  **WinUI** стабильного канала нет типов, которые проецирует профиль `full`:
  `WrapPanel`, `LayoutPanel`, `FlowLayout`, `PagerControl` и элементов
  рукописного ввода. Среда этого канала устанавливается для текущего
  пользователя рядом со стабильной; без неё приложение не запустится.
  Сценарий `tools/install-runtime.ps1` берёт её установщики из пакета
  `Microsoft.WindowsAppSDK.Runtime`, каталог которого называет список
  восстановления (`build/x64/wxl.packages/restored-packages.json`), поэтому
  сценарий запускается после настройки. Метку выпуска и основную версию, по
  которым приложение запрашивает пакет платформы Windows App Runtime
  (`Microsoft.WindowsAppRuntime.2-experimentalF`), загрузчик **wxl** берёт из
  заголовка `WindowsAppSDK-VersionInfo.h` того же пакета.
- **Обёртки — шаг сборки:** сборка собирает генератор `winui-srcgen`,
  запускает его с профилем `wxl.gen/profiles/full.winxl-profile` и
  компилирует то, что он написал, в `wxl.ui`. Обёртки лежат в каталоге сборки,
  `build/x64/wxl.ui/full/wxl`: заголовки подключаются как `<wxl/X.h>`, а тела
  собраны в восемь единиц трансляции `parts/wrapper-00.cpp` …
  `wrapper-07.cpp` (функция `wxl_add_ui_profile`,
  `cmake/wxl_ui_profile.cmake`). Описаний из документации метаданных в них нет
  никогда: сайт документации генерирует свои (см. «Сайт документации»), и ни
  он, ни его язык не меняют того, что компилирует библиотека. Генератор
  запускается снова, когда меняется он сам, любой файл каталога
  `wxl.gen/profiles` (и каталога профиля, если тот лежит не там) или список
  восстановления пакетов, и переписывает только изменившиеся файлы; сборка
  компилирует заново только изменившиеся части и исходники, которые включают
  изменившиеся заголовки. Список заголовков сборка берёт из каталога обёрток
  при настройке, поэтому сборка после первой, как и после запуска, который
  добавил или убрал заголовок, сначала настраивает дерево заново. Debug и
  Release одного каталога сборки пишут в один и тот же каталог обёрток и
  запускают генератор под одним именем, `build/x64/wxl.gen/winui-srcgen.exe`
  (копия, которую обновляет каждая компоновка генератора): сборка другой
  конфигурации запускает генерацию снова, только если её генератор собран
  заново.
  Каталог `wxl.ui/src/wxl` с обёртками, сгенерированными в исходники,
  останавливает настройку: его заголовки нашлись бы на пути включения раньше
  сгенерированных сборкой, и его нужно удалить.
- **Все примеры сразу:** сценарий `run-samples.bat` собирает их в
  конфигурации Debug и предлагает запустить любой из списка.
- **Сайт документации:** значение `WXL_BUILD_DOCS=OFF` сохраняется в кэше.
  Чтобы собрать сайт документации и его тест, выполните
  `tools/build.ps1 -Define WXL_BUILD_DOCS=ON`.
- **Расположение примеров:** собранный пример находится в
  `build/x64/samples/<Папка>/<Конфигурация>/<цель>.exe` вместе с ресурсами и
  DLL. Список целей приведён в `samples/README.md`.

## Сборка

Сценарий `tools/build.ps1` сам поднимает окружение Visual Studio с
закреплённым набором инструментов (другой задаётся ключом `-Toolset`) и
настраивает каталог `build/x64`, если тот ещё не настроен:

```powershell
tools\build.ps1                                   # всё, Debug
tools\build.ps1 -Target sample.calc               # одна цель
tools\build.ps1 -Configure                        # настроить заново
tools\build.ps1 -Define WXL_BUILD_DOCS=OFF,WXL_BUILD_BENCHMARKS=ON
```

В Developer PowerShell набор инструментов берётся из уже поднятого
окружения, и ключ `-Toolset` там игнорируется. В этой среде можно
использовать пресеты: `cmake --preset x64`, затем
`cmake --build --preset x64-debug` или `x64-release`. Ключи `-Define`
сохраняются в `CMakeCache.txt`. Список ключей через запятую разбирает
PowerShell; при запуске из `cmd` (`pwsh -File`) он передаётся одной строкой,
поэтому оттуда задаётся по одному ключу за запуск.

| Ключ | По умолчанию | Что делает |
| --- | --- | --- |
| `BUILD_TESTING` | `OFF` | Включает тесты GTest; пресеты этот ключ не задают. |
| `WXL_BUILD_DOCS` | `ON` | Включает сайт документации Doxygen: цель `docs`, результат — `build/x64/docs/wxl/html/index.html`. На то, что компилирует библиотека, не влияет. |
| `WXL_DOC_LANGUAGE` | `en` | Язык сайта и описаний в обёртках, которые генерирует для него цель `docs`: код папки справочника Windows SDK, который сборка передаёт генератору как `--doc-language` (см. «Сайт документации»). |
| `WXL_BUILD_BENCHMARKS` | `OFF` | Включает бенчмарки `wxl.core`, `wxl.async`, `wxl.fmt`, `wxl.ui`. |
| `WXL_STRICT_CORO` | `OFF` | Оставляет проверки корутин `wxl.async` в любой конфигурации сборки, а не только в Debug (см. [«Асинхронность»](async.md)). |
| `WXL_ENABLE_PCH` | `ON` | Включает предкомпилированный заголовок `src/pch.h` у `wxl.core` и `wxl.async`. Модульные единицы из него исключены (MSVC не принимает его перед объявлением модуля), поэтому ключ влияет только на время сборки обычных единиц трансляции. |
| `WXL_INSTALL` | `ON` у `wxl.core`, настроенного самостоятельно; в общем дереве — `OFF`, чтобы `cmake --install` потребителя не переносил файлы **wxl** в его префикс | Включает правила установки `wxl.core` (см. ниже, «`wxl.core` отдельно»). |
| `WXL_UPDATE_INTELLISENSE` | `OFF` | Только у `wxl.core`, настроенного самостоятельно: после сборки из среды разработки обновляет конфигурацию IntelliSense VS Code (см. [«Работа в редакторе»](editor.md)). |

Сквозная оптимизация (`/GL`, LTCG) не используется. Это решение принято по
замеру, записанному в корневом `CMakeLists.txt` (сентябрь 2026). Без неё пул
памяти работает быстрее: 28.4 нс против 31.7 на глубоком сценарии и 38.8
против 48.9 на мелком. Проверка UTF-8 ускоряется на 18 %, разбор XML не
меняется, а исполняемые файлы отличаются в пределах процента. Кроме того,
объектные файлы с `/GL` содержат промежуточное представление вместо кода:
статические библиотеки дерева вырастают с 42 МБ до 1.7 ГБ, а каждая
компоновка Release перекомпилирует программу целиком.

## Пакеты NuGet и проекция cppwinrt

Пакеты NuGet, по которым собирается дерево, и проекцию C++/WinRT над ними
создаёт настройка. Сценарий `cmake/wxl_packages.cmake` записывает в каталог
сборки вспомогательный проект MSBuild `wxl.packages/wxl.packages.vcxproj` без
исходников и запускает на нём MSBuild той установки Visual Studio, из
окружения которой выполняется настройка (`VSINSTALLDIR`):

```
MSBuild.exe wxl.packages.vcxproj -restore -t:ResolveReferences,CppWinRTMakeProjections
```

- **Закрепления.** Пакеты, на которые ссылается проект, перечислены в
  списке `packages` файла `tools/packages.json`: зонтичный пакет
  `Microsoft.WindowsAppSDK` выпуска Windows App SDK, зависимости которого —
  пакеты выпуска, а также Win2D, WebView2 и `Microsoft.Windows.CppWinRT`.
  Версия закрепления записывается в одной из двух форм:
  - `"version": "1.4.0"` — минимум: восстановление берёт новейшую версию той
    же старшей (major) версии и того же канала, не ниже минимума;
  - `"version": "[1.4.0]"` — ровно одна версия в квадратных скобках:
    восстановление берёт ровно эту версию, и обновление её не меняет.

  Старшую версию минимума повышают только вручную, исправив минимум. Другие
  диапазоны NuGet (`[1.4.0, 2.0.0)`, `(1.4.0, )`, `[1.4.0,1.4.0]`)
  останавливают настройку: закрепление — либо минимум, либо одна версия в
  скобках. Удержание на одной версии нужно спутникам выпуска — Win2D,
  WebView2, `Microsoft.Windows.CppWinRT`: каждый из них выходит сам по
  себе, и новая версия спутника может требовать компонент Windows App SDK
  новее того, что есть в выпуске, который закрепляет зонтичный пакет. Тогда
  проверка компонентов пакета `Microsoft.WindowsAppSDK.Runtime`
  (`VerifyReferencedWindowsAppSdkComponentVersions`) останавливает
  восстановление, и единственный способ оставить спутник на прежней версии —
  удерживать его на ней, пока выпуск не сдвинется. Удержание — временная
  мера до выхода выпуска, который удовлетворяет спутник. Обычный ответ на
  спутник, которому нужен более новый компонент, — сдвинуть выпуск вперёд
  обновлением, а не удерживать спутник: дерево следует за новейшими
  версиями своего канала. Сейчас канал — `experimental` (минимум
  `Microsoft.WindowsAppSDK` несёт метку); когда все типы, которые
  проецирует профиль `full` (WrapPanel, LayoutPanel, FlowLayout,
  PagerControl и типы Ink), выйдут в стабильном выпуске, минимум
  переписывается на эту стабильную версию, и обновление дальше берёт
  новейший стабильный выпуск. Более старые версии Windows App SDK не
  поддерживаются: среда выполнения обновляется через Microsoft Store, а не
  вместе с Windows, и потребителю старая версия ничего не даёт. Сейчас ни
  один пакет не удерживается: все закрепления — минимумы.
- **Канал.** Минимум без метки предварительного выпуска допускает только
  стабильные версии. Минимум с меткой называет канал словом, с которого
  метка начинается, — буквами до первого символа, который не буква:
  `2.5.4-experimental` относится к каналу `experimental`. Такой минимум
  допускает версии, метка которых начинается с этого слова без учёта
  регистра: выпуски Windows App SDK одного канала называются
  `2.2.2-experimental9`, `2.3.2-experimentala`, `2.5.4-experimental`.
  Поэтому минимум канала записывается с голым словом канала, как
  `2.5.4-experimental`: минимум, метка которого несёт суффикс выпуска
  (`2.3.2-experimentala`, `2.2.2-experimental9`), называет каналом слово
  вместе с этим суффиксом и не допускает других выпусков канала.
  Версии сравниваются по правилам NuGet (`cmake/wxl_nuget_version.cmake`,
  тест — `ctest -R nuget-version`).
- **Ссылки проекта.** Закрепление `[X]` попадает во вспомогательный проект
  как записано. Стабильный минимум `M.m.p` превращается в плавающую
  версию NuGet `M.*`: новейшую стабильную версию старшей версии `M`.
  Плавающей версии одного канала у NuGet нет: `2.*-experimental*` берёт и
  стабильные версии, а стабильная версия старше любого предварительного
  выпуска с теми же или меньшими номерами. Поэтому минимум с меткой
  превращается в точную версию `[X]`, где `X` — версия, записанная в файле
  блокировки, или та, которую выбирает обновление.
- **Файл блокировки.** Восстановление записывает выбранные версии в
  `tools/packages.lock.json`, и этот файл входит в репозиторий: новая версия
  приходит только с обновлением, которое переписывает файл. CI
  восстанавливает пакеты в режиме блокировки (переменная окружения
  `RestoreLockedMode=true`): NuGet берёт версии, записанные в файле, и
  останавливает восстановление, если файл не соответствует закреплениям. Файла,
  которого нет, NuGet в этом режиме не требует, а записывает его заново,
  поэтому настройку в режиме блокировки без файла останавливает
  `cmake/wxl_packages.cmake` ещё до запуска MSBuild.

  Вне обновления файл блокировки и закрепления соответствуют друг другу, и
  настройка это проверяет до запуска MSBuild: у каждого закрепления есть
  прямая запись в файле, у файла нет прямых записей, которых нет среди
  закреплений, а ссылка каждого закрепления — та, для которой записана
  запись, её диапазон `requested` (`M.*` записывается как `[M.*, )`, `[X]` —
  как `[X, X]`). Если закрепления изменились — добавлено или убрано закрепление,
  поставлено или снято удержание, повышена старшая версия, — NuGet без
  режима блокировки разрешил бы все пакеты заново, сдвинул бы все плавающие
  версии и молча переписал бы файл. Вместо этого настройка останавливается
  и называет обновление: выполнить `tools\build.ps1 -UpdatePackages` в
  дереве **wxl** и зафиксировать `tools/packages.lock.json`. Без обновления
  заново разрешает версии только настройка дерева **wxl** вообще без файла
  блокировки и без режима блокировки: она выбирает версии минимумов с меткой
  так же, как обновление, а восстановление записывает файл.

  Файл блокировки, который пришёл с `git pull` при тех же ссылках, новее
  результата прошлого восстановления. NuGet пропускает восстановление, пока
  хэш его входных данных не изменился, а файл блокировки в этот хэш не
  входит, поэтому настройка удаляет `wxl.packages/obj/project.nuget.cache`, и
  восстановление выполняется заново по файлу. После восстановления версия
  каждого закрепления должна совпасть с записанной в файле; иначе настройка
  останавливается и предлагает удалить `wxl.packages/obj` и настроить дерево
  заново. Повреждённый файл блокировки (например, с маркерами конфликта
  слияния) останавливает настройку: его берут обратно из git или выполняют
  обновление, которое такой файл не читает и пишет заново.
- **Обновление пакетов.** `tools\build.ps1 -UpdatePackages` выполняет
  настройку с `WXL_UPDATE_PACKAGES=ON` и затем сборку. Закрепление `[X]`
  обновление не трогает. Для каждого минимума с меткой настройка загружает
  список версий пакета из плоского контейнера (flat container) источника
  NuGet — переменная кэша `WXL_NUGET_FLAT_CONTAINER`, по умолчанию
  `https://api.nuget.org/v3-flatcontainer` — и берёт из него новейшую версию,
  которую допускает минимум. Список содержит каждую когда-либо
  опубликованную версию, в том числе снятые с публикации (unlisted), и не
  отличает их; обновление берёт новейшую версию списка. Предполагается, что
  плавающие ссылки NuGet выбирают по тому же списку. Восстановление
  выполняется с `RestoreForceEvaluate=true`, чтобы NuGet заново вычислил
  плавающие версии, а не взял их из файла блокировки, и переписывает файл.
  Затем настройка печатает для каждого закрепления версию до и после
  обновления (`NuGet update: <пакет> <было> -> <стало>`); эти строки и
  изменение `tools/packages.lock.json` разработчик проверяет, прежде чем
  зафиксировать файл. Переключатель одноразовый: после успешного обновления
  настройка удаляет `WXL_UPDATE_PACKAGES` из кэша, и следующая настройка —
  обычная (после неудачного переключатель остаётся, и следующая настройка
  повторяет обновление). Если обновление остановил MSBuild, настройка
  возвращает `tools/packages.lock.json` к тому, каким он был до обновления:
  NuGet записывает файл в конце восстановления, а проверки после него ещё
  могут остановить сборку. Возвращённый файл новее результата
  восстановления, и следующая обычная настройка восстанавливает пакеты по
  нему. Если причина — проверка компонентов пакета
  `Microsoft.WindowsAppSDK.Runtime` (спутнику понадобился компонент новее
  выпуска), либо удерживают спутник на прежней версии `[X]` и повторяют
  обновление, либо настраивают дерево с `-DWXL_UPDATE_PACKAGES=OFF`. Повреждённый файл блокировки обновление не
  читает и пишет заново, а версии до обновления показывает как
  `unreadable`. После восстановления, которое записало файл блокировки,
  настройка обновляет время `wxl.packages/obj/project.nuget.cache`, чтобы
  следующая настройка не приняла файл за пришедший с `git pull`. В режиме
  блокировки и в проекте, который подключает wxl, обновление отказывается
  работать, потому что оба не переписывают файл блокировки.
- **Проекция.** Её строят цели пакета `Microsoft.Windows.CppWinRT`: проекцию
  Windows SDK (`winrt/base.h`, `winrt/Windows.*`) и проекцию метаданных пакетов
  (`winrt/Microsoft.*`, Win2D, WebView2). Результат находится в каталоге
  сборки, `build/x64/wxl.packages/projection`. Цель `Microsoft::CppWinRT`
  передаёт этот каталог своим потребителям как каталог включаемых файлов;
  `wxl.ui` линкует её как `PRIVATE`.
- **Каталоги пакетов.** Каталог каждого пакета настройка берёт из результата
  восстановления, файла `wxl.packages/obj/project.assets.json`, функцией
  `wxl_nuget_package_dir()`. Сами пакеты находятся в глобальной папке пакетов
  NuGet, которую задаёт переменная `NUGET_PACKAGES` или конфигурация NuGet.
- **Список восстановления.** По результату восстановления и файлу ответов
  проекции платформы (`wxl.packages/int/wxl.packages.vcxproj.cppwinrt_plat.rsp`)
  настройка записывает список `wxl.packages/restored-packages.json`. В нём
  перечислены каждый восстановленный пакет — идентификатор, версия, которую
  выбрало восстановление, и каталог — и Windows SDK проекции — его версия и
  файлы `.winmd`, из которых построена проекция платформы (записи `-in` файла
  ответов). Пути абсолютные, с разделителем `/`:

  ```
  {
      "packages": [
          { "id": "Microsoft.WindowsAppSDK", "version": "2.5.4-experimental", "directory": "C:/Users/<имя>/.nuget/packages/microsoft.windowsappsdk/2.5.4-experimental" }
      ],
      "windowsSdk": {
          "version": "10.0.26100.0",
          "metadata": [ "<путь>/<контракт>.winmd" ]
      }
  }
  ```

  Генератор `winui-srcgen` и редактор профилей `wxl.gen.ui` получают этот
  список ключом `--packages`: каждый пакет профиля они читают в той версии и
  из того каталога, которые названы в списке, а метаданные Windows — из
  файлов этого Windows SDK. Без ключа генератор останавливается с ошибкой, а
  редактор показывает ошибку; в обеих сказано, откуда взять список. Тесты
  `wxl.gen` и `wxl.gen.common` получают путь к списку от CMake
  (`wxl_restored_packages_file()`), а `tools/install-runtime.ps1` и
  `run-gen-ui.cmd` берут список каталога `build/x64`. Формат списка и его
  запись описаны в `cmake/wxl_restored_packages.cmake`, тест записи —
  `ctest -R restored-packages`.
- **Что выключено.** Вспомогательный проект выключает интеграцию vcpkg
  (`VcpkgEnabled=false`) и импорт файлов `Directory.Build.props`,
  `Directory.Build.targets` и `Directory.Packages.props` из каталогов выше
  каталога сборки. Набор инструментов и Windows SDK он берёт из окружения
  разработчика (`VCToolsVersion`, `WindowsSDKVersion`). Остальное окружение
  машины на восстановление влияет: MSBuild читает переменные окружения как
  свойства, а NuGet — файлы `NuGet.Config` в каталогах выше каталога сборки и
  конфигурацию пользователя и машины.
- **Повторная настройка.** MSBuild пропускает восстановление и цели, результат
  которых актуален, а список восстановления записывается, только если его
  текст изменился. Обычная настройка читает файл блокировки один раз и не
  загружает списки версий; файл блокировки новее прошлого восстановления
  запускает восстановление заново (см. «Файл блокировки»). Без сети
  обходятся версии и пакеты: версии берутся из файла блокировки, пакеты — из
  глобальной папки пакетов, если они там есть. Но восстановление, которое
  NuGet выполняет заново (после такого файла блокировки и при обновлении),
  проверяет пакеты по индексу уязвимостей NuGetAudit
  (`v3/vulnerabilities/index.json` и файлы, которые он называет): индекс
  берётся из HTTP-кэша NuGet, пока тот свеж (около 30 минут), а потом
  загружается из сети. Аудит во вспомогательном проекте не выключен.
  Изменение `tools/packages.json` или `tools/packages.lock.json` запускает
  настройку при следующей сборке.
- **Ошибки.** Журнал MSBuild записывается в
  `build/x64/wxl.packages/msbuild.log`. Если MSBuild завершается ошибкой или
  результат не тот, что ожидается (нет файла блокировки, нет пакета, нет
  заголовков проекции), настройка останавливается и показывает вывод MSBuild,
  путь к журналу и то, что нужно сделать. После каждого восстановления
  версия каждого закрепления сверяется с ним: версия, отличная от
  удерживаемой `[X]`, или версия ниже минимума, другой старшей версии или
  другого канала останавливает настройку. Файл блокировки тогда не
  соответствует закреплениям, и исправляет это обновление или правка
  закрепления (другую старшую версию берут, только исправив минимум
  вручную). Так же сверяется версия минимума с меткой,
  записанная в файле блокировки, ещё до восстановления. Если список версий
  не загрузился или в нём нет версии, которую допускает минимум, настройка
  останавливается и называет адрес списка, маску вида `2.*-experimental*`,
  минимум и последние версии списка. Кэш каталога сборки, в котором
  записан файл инструментов vcpkg (`CMAKE_TOOLCHAIN_FILE`), тоже останавливает
  настройку: дерево собирается без файла инструментов, и такой каталог
  настраивается заново, `cmake --preset x64 --fresh`.

Чтобы изменить закрепление, исправьте его в `tools/packages.json` — минимум
(`1.4.0`), от которого восстановление берёт новейшую версию той же старшей
версии и того же канала, или одну удерживаемую версию в скобках (`[1.4.0]`),
— выполните обновление (`tools\build.ps1 -UpdatePackages`) и зафиксируйте
изменённый `tools/packages.lock.json` в том же коммите, что и закрепление.
Удерживаемый спутник возвращают к минимуму, когда выпуск Windows App SDK
сдвинулся и содержит нужные ему компоненты.
Чтобы взять более новые версии при прежних закреплениях, достаточно
обновления и коммита файла блокировки. Версия ниже минимума, который называет
профиль (`minimumWindowsAppSdk`, `minimumVersion`), останавливает генератор
(см. [«Проекция и генерация кода»](projection.md)).

## Тесты и бенчмарки

```powershell
tools\build.ps1 -Define BUILD_TESTING=ON
ctest --preset x64-debug                 # из корня: пресет ищется в текущем каталоге
ctest --preset x64-debug -R docs         # сайт документации как тест, при WXL_BUILD_DOCS=ON
```

- **Тесты GTest:** расположены по модулям (`<модуль>/tests` или `/test`);
  общая обвязка находится в `test-support/`. Она включает фикстуру, стенд
  нагрузочных тестов и отдельный каталог для каждого теста и процесса, чтобы
  тесты не мешали друг другу при запуске `ctest -j`.
- **GoogleTest:** версия 1.18.0 приходит с деревом при любой настройке —
  всего дерева или модуля самостоятельно (`wxl.core`, `wxl.xml` и другие):
  сценарий `cmake/wxl_gtest.cmake` загружает её через `FetchContent` и
  собирает тем же стандартом C++23 и с той же CRT, что и тесты, а
  `find_package(GTest)` находит именно эту сборку.
- **Статическая верификация синтаксиса:** цель `wxl.ui.surface-test` выполняет
  компиляцию всего декларативного словаря без запуска кода и собирается без
  путей к проекции cppwinrt. Благодаря этому любое имя `winrt::`, случайно
  просочившееся в публичный заголовок, ломает сборку. В эту
  цель входят сгенерированный файл `parts/schema_surface.cpp`, содержащий по одной
  проверочной строке на каждый элемент из `schema.h`, и рукописный тест
  `wxl.ui/test/dsl_surface.cpp` для валидации компонентов, написанных
  вручную. Действует правило: любое добавление или изменение в `schema.h`
  должно сопровождаться сопутствующей строкой проверки.
- **Узкие интерфейсы пути:** тест `narrow-paths` (`cmake/wxl_narrow_paths.cmake`)
  просматривает исходники и их шаблоны (`*.h.in`), которые отслеживает git, и
  называет файл и строку каждого вызова, который узнаётся по написанию:
  `string()` и `generic_string()` с их формами u8 как члена чего угодно,
  узкого окружения библиотеки C (`getenv`, `_putenv` и соседних), `u8path`,
  открытия файла по узкому имени (`fopen`, `_fsopen`, `_sopen_s` и соседних),
  `std::system` и функций Windows, которые принимают путь или окружение, в
  форме `A` и без суффикса: дерево не определяет `UNICODE`, поэтому имя без
  суффикса означает форму `A`. Путь, построенный из узкого текста в переменной,
  и путь, выведенный в поток оператором `<<`, тест не находит: для этого нужны
  типы. Почему эти интерфейсы запрещены, описано на странице [о тексте](text.md).
  Тест регистрируется в клоне с git; на CI его отсутствие останавливает
  настройку.
- **Бенчмарки:** это отдельные исполняемые файлы, каждый из которых сам
  выводит свою таблицу.

Проверки корутин описаны на странице [об асинхронности](async.md).

## Сайт документации

Сайт строит Doxygen из каталога `docs/` и исходников. В дереве **wxl** это цель
`docs`, доступная при `WXL_BUILD_DOCS=ON`. В сборку по умолчанию она не
входит и строится только по запросу: `tools/build.ps1 -Target docs` или
`cmake --build --preset x64-debug --target docs`.

Каталог `docs` также является самостоятельным проектом CMake без
компилятора:

```
cmake -S docs -B build/docs
cmake --build build/docs --target docs
ctest --test-dir build/docs
```

Doxygen читает исходники, не собирая их, поэтому таким способом сайт можно
построить там, где код не собирается: без MSVC, без настройки дерева **wxl** и
без сгенерированных проекции и обёрток. Обёртки, которые сгенерировала для
сайта сборка дерева, такой сайт описывает, если ключ `WXL_DOCS_WRAPPERS_DIR`
называет их каталог (`-DWXL_DOCS_WRAPPERS_DIR=<сборка>/docs/wrappers/wxl`); без ключа
страниц обёрток **WinUI** на сайте нет. Результат находится в
`build/docs/docs/wxl/html/index.html`.

Опубликованный сайт собирает и публикует автор: с каждым релизом **wxl**, а
до первого релиза — по мере изменений. Он собирается на Windows вместе с
обёртками **WinUI**: целью `docs` дерева при `WXL_BUILD_DOCS=ON`. Перед
Doxygen она генерирует профиль `full` ещё раз, с описаниями, в отдельный
каталог `build/x64/docs/wrappers/wxl` (цель `docs.wrappers`, которая в сборку
по умолчанию не входит), поэтому на сайте есть страницы обёрток, а у типов,
для которых пакет поставляет документацию, — и их описания. Цель `docs` ждёт
генерации, так что Doxygen не читает каталог, который генератор ещё пишет. Для pull request сайт собирается на Linux без
обёрток и не публикуется: эта сборка проверяет, что Doxygen разбирает
комментарии дерева без предупреждений.

Язык сайта задаётся в одном месте — ключом `WXL_DOC_LANGUAGE` (по умолчанию
`en`), который сборка передаёт генератору как `--doc-language`. На этом языке
приводятся подписи, которые ставит Doxygen, и описания типов Windows там, где
справочник Windows SDK есть на этом языке; описания типов Windows App SDK
всегда английские, статьи сайта остаются русскими, а краткое описание проекта
русское только при `ru`. С флагом
`--docs` генератор записывает код языка и его имя для Doxygen в файл
`doc_language.txt` рядом с обёртками. Язык известен только после генерации,
поэтому настройка его не читает: шаг сборки `docs.language` после генерации
читает этот файл и пишет `build/x64/docs/language.doxyfile` с языком и
кратким описанием, который Doxyfile сайта включает последним
(`docs/language.cmake`); если файла нет, подписи английские. Имена языков для
Doxygen записаны в одном месте — в таблице генератора. Подписи и описания
обёрток опубликованного сайта — английские. Тест `docs` сначала собирает
`docs.language`, а с ним и генерацию обёрток сайта.

Требуется Doxygen версии 1.18 или новее: это первый выпуск, который создаёт
из `export module` страницу модуля. Если в системе такой версии нет,
настройка сама скачивает закреплённую сборку 1.18.0 для Windows или Linux; на
других системах Doxygen необходимо установить вручную. Тема оформления
`doxygen-awesome-css`, закреплённая по коммиту, также загружается при
настройке (`cmake/wxl_doxygen.cmake`).

## Свой проект

Приложение на **wxl** объявляется функциями из каталога `cmake/`. Так выглядит
`samples/Quadratic/CMakeLists.txt`:

```cmake
wxl_add_executable(sample.quadratic
    main.cpp
)

target_link_libraries(sample.quadratic PRIVATE wxl::fmt)

wxl_target_icon(sample.quadratic app.ico)
wxl_target_assets(sample.quadratic Assets)
```

- **`wxl_add_executable(<цель> <исходники>…)`:** объявляет оконный exe с
  точкой входа из `wxl::ui` и вызывает `wxl_target_manifest` и
  `wxl_target_runtime`.
- **`wxl_target_manifest(<цель>)`:** добавляет к цели манифест из
  `cmake/wxl_app.manifest.in` с её именем: проверенную версию Windows,
  собственный масштаб для каждого монитора и кодовую страницу UTF-8.
  Консольный инструмент, объявленный через `add_executable`, вызывает её сам,
  как `winui-srcgen`. Цель с собственным манифестом в исходниках остаётся при
  нём.
- **`wxl_target_runtime(<цель>)`:** размещает рядом с exe DLL загрузчика
  Windows App Runtime, Win2D и `WebView2Loader.dll`. Вызывать её вручную
  требуется только для цели, объявленной иначе.
- **`wxl_target_icon(<цель> <файл.ico>)`:** добавляет значок в ресурсы exe.
  Этот же значок **wxl** назначает окнам без собственного значка и значку в
  трее.
- **`wxl_target_assets(<цель> <папка>)`:** размещает папку рядом с exe, по
  правилу на каждый файл. Адрес ресурса без схемы (`u"Assets/logo.png"`)
  ищется там же.

В исходниках подключаются заголовки `wxl.ui` (`ui.h` и соседние, как в
`samples/HelloHere/pch.h`) и определяется функция
`wxl::Teardown wxl_launched()`, объявленная в `launch.h`. Проще всего
создать папку в `samples/` и добавить строку в `samples/CMakeLists.txt`.
Приложению, которое само обращается к проекции C++/WinRT, её заголовки даёт
цель `Microsoft::CppWinRT`: `target_link_libraries(<цель> PRIVATE
Microsoft::CppWinRT)`, как в `sandbox/LightingLab/CMakeLists.txt`.

### Рядом с деревом wxl

Проект, расположенный рядом с деревом **wxl**, подключает его подкаталоги.
Порядок при этом важен. Ворота `import std;` открываются до `project()`: UUID
ворот привязан к выпуску CMake, и открыть их может только верхний уровень.
Стандарт и модули задаются до первого подкаталога. Обёртки дерева **wxl** к
этому моменту должны быть сгенерированы, а пресет проекта должен задавать
Ninja; проще всего взять `CMakePresets.json` из wxl.

Пакеты NuGet и проекцию `wxl.ui` получает сама: её `CMakeLists.txt`
подключает `cmake/wxl_packages.cmake`, и вспомогательный проект появляется в
каталоге сборки проекта. Поэтому проект настраивается из окружения
разработчика с компонентом C++ WinUI (см. «Требования»). Своей цели
`Microsoft::CppWinRT` (её определяет, например, пакет `cppwinrt` из vcpkg) в
проекте быть не должно: две проекции в одной сборке останавливают настройку.

Проект, который подключает **wxl** (подкаталогом или через `FetchContent`),
восстанавливает пакеты в режиме блокировки: настройка передаёт MSBuild
`-p:RestoreLockedMode=true`, берёт версии из файла блокировки дерева **wxl**,
`tools/packages.lock.json`, и этот файл не переписывает. Если файла в дереве
**wxl** нет или в нём не записана версия минимума с меткой, настройка
проекта останавливается; обновление пакетов (`WXL_UPDATE_PACKAGES`) в таком
проекте тоже останавливает настройку и выполняется в дереве **wxl**.

```cmake
cmake_minimum_required(VERSION 4.3)

set(WXL_ROOT "${CMAKE_CURRENT_SOURCE_DIR}/../wxl")
include("${WXL_ROOT}/cmake/wxl_import_std_gate.cmake")

project(MyApp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_MODULE_STD 1)
set(CMAKE_CXX_SCAN_FOR_MODULES ON)
add_compile_options(/permissive- /utf-8)

include("${WXL_ROOT}/cmake/wxl_helpers.cmake")

foreach(module wxl.core wxl.xml wxl.fmt wxl.async wxl.html wxl.bb wxl.highlight wxl.rsdn)
    add_subdirectory("${WXL_ROOT}/${module}/src" "${module}" EXCLUDE_FROM_ALL)
endforeach()
add_subdirectory("${WXL_ROOT}/wxl.ui" wxl.ui EXCLUDE_FROM_ALL)

wxl_add_executable(myapp main.cpp)
wxl_target_assets(myapp Assets)
```

### FetchContent

Исходники **wxl** собираются вместе с проектом потребителя, тем же компилятором
и с теми же флагами. Поэтому каждый `.ixx` на всё дерево сборки компилируется
лишь однажды — при сборке самой библиотеки:

```cmake
cmake_minimum_required(VERSION 4.3)

# ДО project(): гейт CMake для `import std;`. UUID привязан к версии CMake:
# этот — для 4.1–4.3, у 4.4 свой; актуальные лежат в
# cmake/wxl_import_std_gate.cmake внутри wxl.
set(CMAKE_EXPERIMENTAL_CXX_IMPORT_STD "d0edc3af-4c50-42ea-a356-e2862fe7a444")

project(my_app LANGUAGES CXX)

include(FetchContent)
FetchContent_Declare(wxl GIT_REPOSITORY <url> GIT_TAG <tag>)
FetchContent_MakeAvailable(wxl)

add_executable(app main.cpp)
target_link_libraries(app PRIVATE wxl::core)
```

Корневой `CMakeLists.txt` **wxl** при настройке восстанавливает пакеты NuGet и
строит проекцию cppwinrt в каталоге сборки потребителя, в режиме блокировки
(см. «Рядом с деревом wxl»). Поэтому настройка потребителя тоже выполняется из
окружения разработчика той установки Visual Studio, в которой есть компонент
C++ WinUI (см. «Требования»).

### `wxl.core` отдельно

Библиотеку `wxl.core` можно настроить и самостоятельно, с её собственными
пресетами (`wxl.core/CMakePresets.json`, каталог сборки
`wxl.core/build/x64`). В этом случае у неё включён `WXL_INSTALL`, и она
формирует правила установки. Приложению на `wxl.ui` необходим вариант
«рядом с деревом».

## Release и дефект MSVC

В тулсетах MSVC от 14.51 до сборки 14.53.36911 конфигурация **Release**
(`/O1` или `/O2` вместе с `/EHsc`) собиралась с дефектом: компилятор не
вызывал деструкторы локальных переменных корутины, у которой `final_suspend`
возвращает `std::suspend_never`, и не освобождал её кадр, если считал, что
тело корутины не бросает исключений. Дефект проявлялся в MSVC для x64; с
`/Od` или `/EHa` код работал верно. Тело `async::task`, которого никто не
ждёт, тоже заканчивается без приостановки, и дефект задевал и его;
поскольку завершение приложения тогда ждало, пока не останется живых
кадров корутин, демонстрационные примеры, собранные с `-Config Release`,
могли зависнуть при закрытии окна. Подробный отчёт — в `bugs/coro-report.md`.

В тулсете 14.53.36911 дефект исправлен: репро из отчёта под `/O2 /EHsc`, с
`/std:c++20` и с `/std:c++latest`, вызывает деструкторы и освобождает кадр
(проверено в октябре 2026 г.). Release собирается и проверяется наравне с
Debug.

**На старых тулсетах** обход прежний: собирайте в конфигурации **Debug**,
без оптимизации (`/Od`) или с асинхронной моделью исключений (`/EHa`).
