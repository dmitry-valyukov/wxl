# Обработка текста и разметка контента

## Текстовая подсистема и Unicode

Работа со строковыми данными в модуле `wxl.core` (`unicode.ixx`) базируется
на разделении контейнеров на невладеющие виды (view) и владеющие тексты,
разграниченные по кодировкам:

- Виды: `wxl::core::u8_view` и `wxl::core::u16_view`.
- Владеющие контейнеры: `wxl::core::u8_text` и `wxl::core::u16_text`.

Входные текстовые данные из внешних источников проходят проверку один раз,
на границе подсистемы, с помощью функции `checked()`. В участках кода, где
корректность данных обеспечена архитектурно, используется `assume_valid()`
с документированным обоснованием, почему проверка не нужна.

**Пути.** Путь хранится в UTF-16 (`std::filesystem::path` или
`wxl::core::path`) от места, где он получен, до вызова системы: Windows
передаёт и принимает пути в UTF-16, а имя файла не обязано быть правильным
UTF-16. Текстом путь становится только на границе с текстом — в сообщении,
журнале, файле JSON или XML, в библиотеке, которая принимает UTF-8, — через
`wxl::core::unicode::to_utf8()`, где непарный суррогат заменяется на U+FFFD.
Обратный переход, от проверенного текста к пути, выполняет
`wxl::core::unicode::to_path()`, а переменную окружения читает
`wxl::core::environment::variable()`. Узкие интерфейсы пути (`string()`,
`generic_string()`, путь из `std::string` или `std::string_view`) и
`std::getenv` в MSVC проходят через кодовую страницу ANSI процесса, поэтому в
исходниках не используются: имя из метаданных, из профиля или из файла
настроек становится путём через `to_path()`, проверенное там, где текст
пришёл извне. Тест `narrow-paths` находит по написанию те из этих интерфейсов,
что узнаются без типов.
Манифест исполняемых файлов **wxl** объявляет процессу кодовую страницу UTF-8,
чтобы и сторонний код в процессе получал UTF-8.

Границы символов определяются по графемным кластерам стандарта Unicode:
их находят компоненты `wxl::core::unicode::grapheme_breaker`,
`next_grapheme_boundary` и `floor_grapheme_boundary`, так что суррогатные
пары и комбинируемые символы не разрываются. Принадлежность кодовой точки к
буквам определяется функцией `is_letter` по общей категории Unicode `L`
(`Lu`, `Ll`, `Lt`, `Lm`, `Lo`).

**Генерация таблиц свойств.** Таблица свойств Unicode
(`wxl.core/src/grapheme_data.inc`) формируется утилитой
`wxl.core/tools/gen-grapheme-table.py`. Файл поставляется в сгенерированном
виде и не участвует в регулярном цикле сборки, поскольку обновляется раз в
год с выходом новых версий стандарта Unicode. Сценарий генератора написан
на языке Python, а развёртывание интерпретатора и его зависимостей
обеспечивает менеджер [uv](https://docs.astral.sh/uv/) на основании
встроенных в шапку скрипта метаданных. Запуск из корневой директории:

```
uv run wxl.core/tools/gen-grapheme-table.py
```

Сценарий загружает с сервера `unicode.org` пять исходных файлов фиксированной
версии (переменная `UNICODE_VERSION` в теле скрипта, локальный кэш —
`build/unicode/<версия>`) и перезаписывает два файла: саму таблицу и
официальный тестовый файл `wxl.core/tests/data/GraphemeBreakTest.txt` той
же версии. Для перехода на новую версию Unicode достаточно обновить значение
`UNICODE_VERSION`, запустить генератор и выполнить тесты `wxl.core.tests`,
которые проверяют правила разбиения на графемы по всем случаям тестового
файла и бит буквы для `is_letter`.

## Форматирование строк

Компонент `wxl.fmt` предоставляет строковый сборщик `wxl::core::text_builder`
и функцию `format`. Подсистема построена поверх библиотеки `fmt`, которая
компилируется модулем `import fmt;` из собственного исходного кода; ядро
`wxl.core` от внешнего кода не зависит. Подробное описание и замеры
производительности — [`wxl.fmt`](fmt.md).

## Парсеры XML и JSON

Компоненты `wxl::xml` и `wxl::json` реализуют разбор буфера целиком:
переданный буфер памяти переходит читателю и проверяется полностью,
результирующее дерево формируется в виде видов (view) на исходный буфер, а
узлы размещаются в арене, развёрнутой поверх пула памяти текущего потока.
Парсер JSON всегда поддерживает комментарии, так как этот формат
используется для описания профилей утилиты `winui-srcgen`.

## Обработка и разметка внешнего контента

Модули `wxl.html`, `wxl.bb` и `wxl.rsdn` предназначены для синтаксического
разбора и визуализации неконтролируемого внешнего контента (текст форумов,
чатов, сторонних сообщений) без привлечения тяжеловесного компонента
`WebView`. Алгоритмы разбора устойчивы к синтаксическим ошибкам:
некорректные или неизвестные теги игнорируются, а вложенное в них текстовое
содержимое сохраняется.

Все три парсера строят одно дерево, отображением которого занимаются
графические элементы `wxl::HtmlBlock`, `wxl::BbBlock` и `wxl::RsdnBlock`,
построенные на базе нативного `RichTextBlock`. Подробное описание
архитектуры слоя разметки приведено в документе
[«`wxl.html`: подмножество HTML для `RichTextBlock`»](html.md).

Подсистема подсветки синтаксиса `wxl.highlight` поддерживает 31 язык
программирования и оперирует статическими таблицами правил: комментарии
распознаются по открывающим и закрывающим последовательностям, строковые
литералы — по границам кавычек с учётом экранирования, ключевые слова — по
границам слов. Регулярных выражений в реализации нет.

## Журналирование

Компонент `wxl.logging` предоставляет подсистему ведения журнала,
построенную по принципу «одна строка — один вызов». Если уровень важности
сообщения ниже активного порога, вызов стоит одного сравнения. Проверка
форматной строки и типов аргументов выполняется на этапе компиляции, а
асинхронная половина журнала пишет из собственного потока.
