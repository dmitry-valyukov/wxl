# `wxl.html`: подмножество HTML для `RichTextBlock`

## Зачем

Наполнять `RichTextBlock` форматированным содержимым — сообщение форума,
лента чата, справка — декларативно и без WebView. HTML здесь — формат
*входных данных*, зачастую чужих и кривых, а не язык вёрстки приложения:
парсер обязан пережить любой мусор и извлечь из него лучший возможный текст.

HTML — не единственный такой формат. Форумы, к которым имеет смысл
подключаться, отдают JSON, XML, BB- или RSDN-разметку в плоском тексте
(в `style="color: ..."` их превращает сайт или локальный клиент вроде
Janus для КЫВТ); **принято**: каждой разметке — свой контрол со своим
парсером, а общее у них выносится в базовый класс.

## Семейство: `FormattedBlock` и наследники

Системный `RichTextBlock` запечатан, но наследование wxl.ui живёт на
уровне обёрток: классы проекции без единого поля, состояние — в цепочке
`Impl`, созданной через `make<T>`. Под обёрткой остаётся тот же
WinRT-объект `RichTextBlock`.

- **`FormattedBlock : RichTextBlock`** — примитивные операции
  наполнения, общие для всех разметок: «добавить спан таким-то шрифтом,
  такого-то цвета», стек стилей, ссылки, картинки, встроенные элементы.
  Черновой набор:
  - начать блок (отступы `Margin`, выравнивание) / закончить блок;
  - стек строчных стилей: push/pop (шрифт, кегль, жирность, курсив,
    подчёркивание, зачёркивание, цвет);
  - добавить текст текущим стилем; добавить перенос строки;
  - добавить ссылку (текст + идентификатор → общий `onLink`);
  - добавить картинку (источник, размеры, подсказка);
  - добавить произвольный `UIElement` (`InlineUIContainer`);
  - очистить; место вставки для дописывания живёт здесь же.
- **`MarkupBlock : FormattedBlock`** — общий этаж контролов разметки,
  выросший, когда братья появились на деле: тема (`HtmlTheme`), база
  картинок `baseDirectory()`, реестр именованных стилей и общий сборщик,
  обходящий дерево семейства (`MarkupBlock.cpp`).
- **`HtmlBlock : MarkupBlock`** — парсер HTML-подмножества поверх этих
  примитивов. **`BbBlock` и `RsdnBlock` стоят рядом** (**сделано**): свои
  только токенизаторы — модули `wxl.bb` и `wxl.rsdn`, строящие то же
  дерево через `tree_builder` (`wxl.html:builder`) — стек, автозакрытие,
  браузерное восстановление, пробелы и терминированные виды у них общие с
  HTML и отлажены один раз. Отличия записаны в самих модулях: у форумных
  разметок значим перевод строки, незнакомый тег остаётся буквальным
  текстом, сущностей нет; RSDN добавляет построчные цитаты
  («AVK> так и было» складывается в blockquote с видимым префиксом, а
  стрелки — вложенность), языковые теги кода ([c#], [nemerle]…) с
  подсветкой через `wxl.highlight` (куски кода — `<span style="kw">`,
  `"str"`, `"com"`), смайлы форума картинками и адреса прямо в тексте.

Предполагаемое употребление:

```cpp
HtmlBlock {
    html = L"Привет, <b>мир</b>! Подробности <a href='faq'>тут</a>.",
    onLink = [](std::wstring_view href) { ... },
}
```

Две операции над содержимым, обе доступны после постройки:

- **Замена**: присваивание `html` полностью заменяет `Blocks()`.
- **Дописывание**: содержимое добавляется в конец, ничего не перестраивая
  (**принято**: лента чата дополняется, а не пересоздаётся — полная замена
  на каждое сообщение это путь WebView, и именно от него мы уходим).
  **Принято**: семантикой «всегда новый абзац» не ограничиваемся —
  строчное содержимое продолжает последний абзац, блочные теги открывают
  новые.
- **Принято про DSL**: декларативная запись только создаёт — в ней
  остаётся присваивание `html = ...`. Дописывание — обычные процедурные
  методы `append*()` на обёртке.
- **Главное правило процедурной вставки — принято**: каждая вставка
  закрывает все блоки; если вход по ошибке не закрыл — закрываем мы.
  Причина: между вставками не хранится ни исходный HTML, ни состояние
  парсера, и ничто не разбирается заново, когда контент приходит кусками.
  Кусок самодостаточен: незакрытый `<b>` не перетекает в следующий
  `append`.

Голый текст без блочных тегов заворачивается в неявный `Paragraph`:
сообщение чата «просто текст с `<b>`» обязано работать без обвязки.

## Кодировка входа

Два явных входа, без угадывания по типу:

- `std::wstring_view` — широкая строка, непосредственный вход
  (литералы DSL, текст от Windows);
- `wxl::core::u8_view` — уже проверенный UTF-8 (текст, прошедший через
  `wxl::core`, — например, принятый из сети и верифицированный наверху).

**Принято** в таком виде: широкая — непосредственная, `u8_view` — наша,
верифицированная.

## Слои внутри `HtmlBlock`

- **Ядро** — токенизатор, сущности, нормализация пробелов, восстановление
  после ошибок; результат — **свой легковесный DOM** (**принято**). Чистый
  C++ без следа WinUI; тестируется обычными тестами wxl: HTML на входе,
  сериализованный DOM на выходе, golden-сравнение.
- **Сборщик** — обход DOM, зовущий примитивы `FormattedBlock`. Правило
  границы то же, что у всей библиотеки: `winrt::` наружу не протекает.

DOM здесь — рабочая структура одного вызова, а не хранилище: построен,
обойдён, выброшен (см. правило вставки — ни HTML, ни DOM между вызовами
не живут). Нужен он потому, что и восстановление вложенности, и
нормализация пробелов, и golden-тесты — операции над деревом, а не над
потоком токенов.

**Хранение DOM — по образцу `wxl.xml`** (**принято**): арена блоками из
STA-пула, дети — `wxl::core::intrusive_slist` через поле в самом узле, один
конкретный тип узла с `node_type` вместо иерархии с vptr, атрибуты —
`std::span` в арене; ни одного лишнего STL-контейнера на узел. Отличие
одно: wxl.xml раздаёт виды в исходный буфер, а HTML-текст после сущностей
и схлопывания пробелов исходному не равен — но и это арена уже умеет,
`copy_text` возвращает вид на свою копию.

Ядро — **не `wxl.xml`**: форумный HTML в природе не well-formed
(`<br>` без закрытия, `&nbsp;`, кавычки где попало), а `wxl.xml` по замыслу
отвергает документ целиком. Толерантность — требование, а не уступка.

## Теги первой очереди

Блочные (у `Block` есть `Margin`, `TextAlignment`, `LineHeight` — отступы
и выравнивание абзацев настоящие):

| Тег | Во что | Примечание |
|---|---|---|
| `<p>` | `Paragraph` с вертикальным `Margin` из `HtmlStyle` | |
| `<div>` | `Paragraph` без отступов | граница блока и только; вложенные `<div>` разворачиваются в плоскую последовательность абзацев, стили наследуются вниз |
| `<br>` | `LineBreak` | |
| `<h1>`–`<h3>` | `Paragraph` + кегль/жирность из стилей | масштабы в `HtmlStyle` |
| `<blockquote>` | `Paragraph` с левым `Margin` + вторичный цвет | фона и рамки у `Paragraph` нет — вертикальную полосу, если захочется, даст только второй очереди `TextHighlighter` или элемент в контейнере |
| `<ul>/<ol>/<li>` | `Paragraph` на пункт: «• » / «1. », висячий отступ левым `Margin` + отрицательным `TextIndent` | вложенность — ростом левого `Margin` |
| `<pre>` | `Paragraph` моноширинным; `\n` → `LineBreak`; пробелы сохраняются | перенос строк отключить нельзя — принимаем |

Строчные:

| Тег | Во что |
|---|---|
| `<b>/<strong>` | `Bold` |
| `<i>/<em>` | `Italic` |
| `<u>` | `Underline` |
| `<s>/<del>` | `Span` + `TextDecorations::Strikethrough` |
| `<code>` | `Run` моноширинным |
| `<a href>` | `Hyperlink` |
| `<img>` | `InlineUIContainer` + `Image` (GIF анимируется сам) |
| `<sub>/<sup>` | `InlineUIContainer` + уменьшенный `TextBlock` со сдвигом: OpenType-путь (`Typography.Variants`) для произвольных букв не работает, а вертикального сдвига у `Run` нет |
| `<font>` | `Span` с цветом/шрифтом/кеглем — **принято: в первой очереди** |

Вторая очередь (**сделано**): `<hr>` — полоса в толщину линии во всю ширину
текста; `<table>` — см. свой раздел; `<details>` со `<summary>` — раскрывашка:
`Expander` без содержимого как заголовок, а содержимое — абзацы того же
блока, которые складка прячет и показывает на месте (`beginFold`/`endFold`
у `FormattedBlock`), так что ничего не вкладывается и выделение идёт
сквозь. Все три — «широкие элементы» (`appendWideElement`): пока блок
переносит текст, они получают ширину текстовой области и следуют за ней
при ресайзе — ширину, которую браузер даёт блочному боксу; при
`TextWrapping::NoWrap` остаются естественной ширины, как и строки.

Ещё не сделано: `<mark>` через `TextHighlighter` и фоновая плашка `<code>`
тем же механизмом.

Сознательно вне рамок: CSS как язык — селекторы, каскад, разбор деклараций
(атрибут `style` поддержан, но значение его — имя зарегистрированного
стиля, см. «Именованные стили»; настоящие источники отдают BB/RSDN/JSON,
а CSS в `style` порождают чужие сайты и клиенты, не мы), скрипты, формы.

## Атрибуты

- `<a>`: `href`.
- `<img>`: `src`, `width`, `height`, `alt`. Размеры **обязательны**:
  картинка грузится асинхронно, без явного размера строка прыгает после
  загрузки. `alt` идёт в `toolTip` — подсказка и имя для диктора разом.
- `<font>`: **принято**
  - `color` — `#rgb` / `#rrggbb` / именованный цвет, полный набор из
    ~140 CSS-имён (это самое дешёвое: одна таблица);
  - `face` — имя семейства, список через запятую — берётся первое;
  - `size` — **семантика ровно как у HTML**: шкала `1`–`7` (умолчание 3)
    и относительные `+n`/`-n`; отображается в множители базового кегля.

## Сущности

Пять XML-ных (`amp lt gt quot apos`), числовые `&#...;` / `&#x...;`,
короткий именованный список: `nbsp mdash ndash laquo raquo hellip copy`.
**Принято**: полный HTML-набор (~250 имён) не нужен. Незнакомая сущность
остаётся литеральным текстом.

## Пробелы

По правилам HTML: цепочки пробельных символов схлопываются в один пробел,
на границах блоков обрезаются, пробельный текст между блочными тегами
выбрасывается; `<pre>` сохраняет всё. Самый крупный раздел тестов ядра.

## Ошибки разметки: текст священен, теги — нет

Контент чужой, поэтому парсер **никогда не выбрасывает исключений на
плохой вход**. Любой мусор на входе → лучший извлекаемый текст на выходе.

- Незнакомый тег отбрасывается, его содержимое остаётся текстом (как в
  браузерах).
- **Перепутанная вложенность — по образцу браузеров** (упрощённый вариант
  их adoption agency algorithm). **Принято** на примере
  `<b>first<i>second</b>third</i>`: `first` — жирный, `second` — жирный
  курсив, `third` — курсив. То есть закрывающий тег закрывает свой элемент,
  а форматирующие элементы, открытые внутри него, переоткрываются следом и
  продолжают действовать.
- Блочный тег внутри строчного принудительно закрывает строчные.
- Непарный закрывающий тег без открытого — игнорируется.
- Одинокий `<`, не начинающий тега, — обычный символ.

## Ссылки

Один обработчик `onLink` на весь блок (живёт в `FormattedBlock`).
Задан — всякий клик идёт в него (сноски, внутренняя навигация). Не задан —
`http`/`https` открываются браузером, остальные схемы гасятся —
для читателя молча, для `onError` записью `BlockedLink`: `javascript:` и
`file:` из чужого контента — не гипотетика.

Что `Hyperlink` не вмещает (перенос строки, картинку, `sub`/`sup`),
ссылка **обходит расщеплением**: элемент встаёт между двумя половинами с
одной целью, порядок текста цел, обе половины кликабельны.

## Картинки

**Принято: только локальные источники** — голый путь, `file://`,
`ms-appx://`, `ms-appdata://`. Остальные схемы отбрасываются с записью
`RemoteImage` в `onError`. На будущее обсуждается событие вида «request
image/video» — парсер встречает внешний источник и спрашивает приложение,
чем его заполнить; записано в TODO, в первую очередь не входит.

Относительный путь разрешается от каталога, названного
`HtmlBlock::baseDirectory()`, — для разметки из файла это каталог файла;
не назван — от рабочего каталога процесса (ресурсы приложения). Картинка,
которая не загрузилась (файла нет, формат бит), обнаруживается
асинхронно и уходит записью `ImageFailed` в тот же `onError`.

## Диагностика: `onError`

Один приёмник на весь блок, живёт в `FormattedBlock` рядом с `onLink`:
всякое восстановление, которое стек по замыслу делает молча, оставляет
запись `HtmlError{kind, detail}` — незнакомый тег, непарный закрывающий,
перепутанная вложенность, кривая сущность, незнакомое имя стиля, кривые
цвет/кегль/размер, картинка без источника или удалённая, погашенный клик.
Ничто из этого не ошибка исполнения — текст всегда выживает; запись
нужна разработчику, который смотрит на экран и не видит там того, что
писал в разметке.

`detail` называет виновника (имя тега, тело сущности, значение атрибута)
и действителен только внутри вызова обработчика, как вид событийных
аргументов. Строительные записи приходят синхронно из `html()`/`append()`
(парсерные — первыми, в порядке входа), `ImageFailed` и `BlockedLink` —
позже, из потока интерфейса. Голый `&` без `;` записи не оставляет:
«Tom & Jerry» — проза, а не битая сущность. Парсер копит свои записи в
`document::errors()` с потолком в несколько десятков: враждебный вход
повторяет свой мусор, а диагностике нужна форма проблемы, не каждый её
экземпляр.

## Таблицы

**Сделано** по этому же предложению. Носитель — `Grid` в `InlineUIContainer`,
стоящем отдельным абзацем; своих таблиц у `RichTextBlock` нет.
Соответствие прямое:

- `<table>` → `Grid` в рамке `Border` (левая и верхняя линии — у рамки,
  правая и нижняя — у каждой ячейки: каждая линия по одному разу; кисть —
  `tableBorderColor` темы, а при пустом поле разделитель темы окна);
- `<tr>` → строка, `<td>`/`<th>` → ячейка: `Border` с `cellPadding` и
  вложенный `FormattedBlock`, так что в ячейке работает вся первая очередь
  и вторая тоже (таблица в таблице — до восьми уровней, глубже плоско);
  `<th>` — жирный, по центру; ссылки и диагностика ячеек уходят в
  обработчики корневого блока;
- `colspan`/`rowspan` → `Grid.ColumnSpan`/`RowSpan` — один в один, с
  раскладкой, которая сдвигает ячейки под объединённой сверху;
- ширины — автоматическая раскладка браузера в её основе: у колонки две
  ширины, max-content (самая широкая ячейка, измеренная без ограничения)
  и min-content (самое длинное неразрывное слово, ячейка измеренная
  нулевой шириной). Влезает по max — колонки `auto`; иначе излишек над
  суммой min делится между колонками пропорционально запасу max − min, в
  пикселях, и ни одна не становится уже своего слова. Пересчёт — при
  каждом изменении ширины полосы. Без переноса текста полоса не
  ограничена, и таблица держит естественную ширину; линейка же во всю
  строку всегда — своей ширины у неё нет.

Что дерево не читает: `width` у колонок и ячеек — вернётся, если попросит
настоящий потребитель.

Честная плата:

- выделение текста не пересекает границу таблицы — содержимое ячеек
  живёт в своих `RichTextBlock`; это единственное место семейства, где
  что-то вложено, и другого носителя у строк и колонок нет;
- таблица не разрывается между колонками `RichTextBlockOverflow`.

**Ответ на бывший главный риск.** `InlineUIContainer` меряет дочерний элемент
шириной строки, но размещает по его желаемой ширине: пустой `Border`
схлопывается в ноль, а `Grid` с колонками `auto` меряет ячейки
бесконечностью и сам не знает, влезает ли. Поэтому широкие элементы
получают ширину явно, от блока, по его `SizeChanged`, а не от контейнера.
Браузеру этот вопрос незнаком: там блочная вёрстка первична, и блочный
бокс получает ширину содержащего блока по определению; здесь первичен
текст, и ширину блочному элементу приходится сообщать самим.

## Именованные стили: `style` без каскада

**Принято.** Атрибут `style` поддерживается, но значение его — не CSS, а
имя заранее зарегистрированного стиля: `<div style="quote">`. Никакого
каскада, селекторов и разбора деклараций — прямой поиск по имени.

- Объект `HtmlStyle` несёт и строчные грани (те же, что `TextStyle`:
  шрифт, кегль, жирность, курсив, подчёркивание, зачёркивание, цвет), и
  блочные (отступы, выравнивание). Блочный тег берёт все грани, строчный —
  только строчные.
- Регистрация — методы `HtmlBlock`:
  - `registerStyle(имя, HtmlStyle)` — один стиль;
  - `registerStyles({{имя, стиль}, {имя, стиль}, ...})` — группа KV-пар
    одним вызовом (`initializer_list` пар).
- Стиль действует на элемент и его содержимое той же механикой, что стек
  строчных стилей, — это наследование вложенности, а не каскад правил.
- **Принято: одно имя на элемент.** Несколько имён через пробел (как у
  `class`) вернутся, только если их попросит настоящий потребитель.
- Незнакомое имя игнорируется: в `style` чужого HTML лежит настоящий
  CSS (`color: red`), и он обязан просто не найтись, а не уронить разбор.
  Для своего же имени с опечаткой это выглядело бы так же — поэтому
  незнакомое имя уходит записью в `onError` (см. «Диагностика»).

## Тема

**Принято и сделано**: `HtmlTheme` (имя — чтобы не сталкиваться с
`HtmlStyle` именованных стилей) — объект со значениями вида: отступы
`<p>`/заголовков/цитаты/`<pre>`, масштабы `h1`–`h3`, цвет цитаты,
моноширинная гарнитура, отступ пункта списка, геометрия `sub`/`sup`,
сторона картинки без размеров. Умолчания — вид первой очереди как есть;
`HtmlBlock::theme()` подменяет объект целиком, действует на всё, что
строится после (уже построенное хранит вид, которым строилось, — как и
именованные стили).

Единственное цветовое умолчание — цвет цитаты — при пустом поле берётся
из ресурса темы `TextFillColorSecondaryBrush` через механизм `brushes.*`
в момент постройки: тёмная и светлая тема получают каждый свой серый.
Выражать тему зарезервированными именами реестра стилей (бывший открытый
вопрос) не стали: у темы есть грани, которых у `HtmlStyle` нет (масштабы,
гарнитура `<pre>`, сторона картинки), и один цельный объект честнее
рассыпанных имён.

## Профиль генератора

Профилю нужен только сам `RichTextBlock` (в `base.json`, рядом с
`TextBlock`). Семейство `Documents` — `Paragraph`, `Run`, `Hyperlink` и
прочие — в профиль **не входит**: наполнение идёт через примитивы
`FormattedBlock`, а их реализация достаёт `Documents` из cppwinrt-проекции
внутри библиотеки, куда `winrt::` и так допущен. Публичных обёрток эти
классы не получают, пока кто-то снаружи не попросит их по имени.
